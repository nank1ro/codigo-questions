# --description--

Todo en este capítulo responde a una pregunta: ¿quién se encarga del fallo?

Una función que lanza errores se niega a responderla. Nombra lo que salió mal — un caso de un enum `Error`, que lleva lo que el gestor vaya a necesitar — y pasa la decisión hacia arriba. Quien llama entonces elige una herramienta: `do`/`catch` para reaccionar caso por caso, `try?` y `??` para recurrir a un valor por defecto, `defer` para limpiar al salir, pase lo que pase.

Esa separación es todo el punto. La función que detecta el problema rara vez sabe qué debería pasar después, y el código que lo sabe rara vez quiere repetir la comprobación.

# --instructions--

Escribe un validador usando todo lo aprendido en este capítulo:
- dale a `FormError` un segundo caso `tooLong` que lleve un `maximum` de tipo `Int`
- `validate` lanza `FormError.empty` cuando el nombre está vacío, lanza `FormError.tooLong(maximum: 10)` cuando tiene más de 10 caracteres y, en caso contrario, devuelve el nombre
- `safeName` devuelve el nombre validado, o `"guest"` cuando `validate` lanza un error

Ejemplo de llamada a la función:
```swift
print(safeName(""))
// imprime guest
```

func _kind(_ name: String) -> String {
    do {
        return try validate(name)
    } catch FormError.empty {
        return "empty"
    } catch FormError.tooLong(let maximum) {
        return "max \(maximum)"
    } catch {
        return "other"
    }
}

# --solutions--

```swift
enum FormError: Error {
    case empty
    case tooLong(maximum: Int)
}

func validate(_ name: String) throws -> String {
    guard !name.isEmpty else {
        throw FormError.empty
    }
    guard name.count <= 10 else {
        throw FormError.tooLong(maximum: 10)
    }
    return name
}

func safeName(_ name: String) -> String {
    return (try? validate(name)) ?? "guest"
}
```

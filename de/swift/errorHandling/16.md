# --description--

Alles in diesem Kapitel beantwortet eine Frage: Wer kümmert sich um den Fehlschlag?

Eine werfende Funktion weigert sich, das zu beantworten. Sie benennt, was schiefgegangen ist — einen Fall eines `Error`-Enums, der alles trägt, was der Handler brauchen wird — und gibt die Entscheidung nach oben weiter. Der Aufrufer wählt dann ein Werkzeug: `do`/`catch`, um Fall für Fall zu reagieren, `try?` und `??`, um auf einen Standardwert zurückzufallen, `defer`, um so oder so beim Verlassen aufzuräumen.

Genau diese Trennung ist der ganze Sinn. Die Funktion, die das Problem erkennt, weiß selten, was als Nächstes geschehen soll, und der Code, der es weiß, will die Prüfung selten wiederholen.

# --instructions--

Schreibe einen Validator mit allem aus diesem Kapitel:
- gib `FormError` einen zweiten Fall `tooLong`, der ein `maximum` vom Typ `Int` trägt
- `validate` wirft `FormError.empty`, wenn der Name leer ist, wirft `FormError.tooLong(maximum: 10)`, wenn er länger als 10 Zeichen ist, und gibt sonst den Namen zurück
- `safeName` gibt den validierten Namen zurück, oder `"guest"`, wenn `validate` wirft

Beispiel für einen Funktionsaufruf:
```swift
print(safeName(""))
// gibt guest aus
```

func _kind(_ name: String) -> String {
    do {
        return try validate(name)
    } catch FormError.empty {
        return "empty"
    } catch FormError.tooLong(let maximum) {
        return "max \(maximum)"
    } catch {
        return "other"
    }
}

```swift
enum FormError: Error {
    case empty
    case tooLong(maximum: Int)
}

func validate(_ name: String) throws -> String {
    guard !name.isEmpty else {
        throw FormError.empty
    }
    guard name.count <= 10 else {
        throw FormError.tooLong(maximum: 10)
    }
    return name
}

func safeName(_ name: String) -> String {
    return (try? validate(name)) ?? "guest"
}
```

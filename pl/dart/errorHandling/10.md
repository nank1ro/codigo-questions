# --description--

`Exception` jest interfejsem, więc twoja własna klasa też może nim być. Własny wyjątek nadaje niepowodzeniu nazwę, którą klauzula `on` może wybrać, oraz pola, które procedura obsługi może odczytać:

```dart
class EmptyCartException implements Exception {
  final String message;

  EmptyCartException(this.message);

  @override
  String toString() => 'EmptyCartException: $message';
}

throw EmptyCartException('nothing to pay for');
```

Trzy części warto zachować: `implements Exception`, aby klasa należała do pozostałych niepowodzeń, pole `final` niosące szczegóły oraz nadpisany `toString()`, aby raport o nieobsłużonym wyjątku był czytelny. Bez tego nadpisania Dart wypisuje samą nazwę klasy, a szczegóły giną.

# --instructions--

Zdefiniuj klasę `InvalidEmailException` implementującą `Exception`, z polem `final String` `message` ustawianym przez konstruktor oraz `toString()` zwracającym `'InvalidEmailException: '` wraz z komunikatem.

Potem napisz funkcję `checkEmail`, która przyjmuje `String` `email` i go zwraca, ale rzuca `InvalidEmailException('missing @')`, gdy email nie zawiera `'@'`.

Przykład:
```dart
print(checkEmail('ada@dart.dev')); // ada@dart.dev
```

Rzucony obiekt powinien nieść komunikat `'missing @'` i wypisywać się jako `InvalidEmailException: missing @`

```dart
  test('test3', () {
    try {
      checkEmail('nope');
      fail('--err-t3--');
    } on InvalidEmailException catch (e) {
      expect(e.message, 'missing @', reason: '--err-t3--');
      expect(e.toString(), 'InvalidEmailException: missing @', reason: '--err-t3--');
    }
  });
```

# --solutions--

```dart
class InvalidEmailException implements Exception {
  final String message;

  InvalidEmailException(this.message);

  @override
  String toString() => 'InvalidEmailException: $message';
}

String checkEmail(String email) {
  if (!email.contains('@')) {
    throw InvalidEmailException('missing @');
  }
  return email;
}
```

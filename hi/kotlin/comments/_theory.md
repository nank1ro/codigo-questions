एक **कमेंट** सोर्स कोड के अंदर लिखा गया एक नोट होता है, जो उसे पढ़ने वाले लोगों के लिए होता है। कंपाइलर कमेंट्स को पूरी तरह अनदेखा कर देता है, इसलिए वे कभी भी प्रोग्राम के काम को नहीं बदलते।

सबसे सरल कमेंट **सिंगल-लाइन कमेंट** है: यह `//` से शुरू होकर लाइन के अंत तक चलता है।
```kotlin
// Greets the user
println("Hello")
```
किसी कोड का उद्देश्य क्या है, या वह इस तरह क्यों लिखा गया, यह समझाने के लिए कमेंट्स का उपयोग करें।

---

कमेंट को अपनी अलग लाइन की ज़रूरत नहीं होती: यह उसी लाइन पर कोड के बाद आ सकता है। इसे **ट्रेलिंग कमेंट** कहते हैं, और यह उस विशेष कथन के बारे में छोटा नोट लिखने की अच्छी जगह है:
```kotlin
val retries = 3 // give up after three attempts
```
`//` से लाइन के अंत तक की सब कुछ अनदेखा कर दिया जाता है, जबकि उससे पहले का कोड सामान्य रूप से चलता है।

---

क्योंकि कंपाइलर कमेंट्स को पूरी तरह हटा देता है, कमेंट जोड़ने या हटाने से प्रोग्राम के काम में कभी बदलाव नहीं आता। केवल वही कोड चलता है जो कमेंट **नहीं** किया गया है।

इसी वजह से `//` किसी कोड की लाइन को उसे हटाए बिना बंद करने का एक तेज़ तरीका है। इसे **कमेंट आउट करना** कहते हैं:
```kotlin
var total = 10
// total = total + 5
println(total) // prints 10
```
दूसरी लाइन अब एक कमेंट है, इसलिए `total` `10` ही रहता है। `//` हटाने पर वह लाइन वापस जीवित हो जाती है।

कमेंट आउट करना प्रयोग करते समय सुविधाजनक है, लेकिन सफ़ाई करना याद रखें: लंबे समय तक कमेंट आउट पड़ा कोड आगे इसे पढ़ने वाले को केवल उलझाता है।

---

जब एक कमेंट को एक से अधिक लाइनों की ज़रूरत हो, तो Kotlin **मल्टी-लाइन कमेंट** देता है (जिसे ब्लॉक कमेंट भी कहते हैं): यह `/*` से शुरू होकर `*/` पर समाप्त होता है, और उनके बीच की सब कुछ अनदेखा कर दिया जाता है — लाइन ब्रेक भी।
```kotlin
/*
  Prints the welcome banner.
  Called once when the app starts.
*/
println("Welcome!")
```
एक ब्लॉक कमेंट छोटा होकर एक ही लाइन पर भी रह सकता है: `/* like this */`।

---

`//`, जो लाइन के अंत पर रुक जाता है, के विपरीत एक `/*` कमेंट केवल `*/` पर रुकता है। यदि आप उसे बंद करना भूल जाते हैं, तो कंपाइलर उसके बाद के पूरे कोड को कमेंट का हिस्सा मानता है और त्रुटि देता है:
```kotlin
val width = 10 /* in centimetres
println(width) // still inside the comment: error, the comment is never closed
```
`//` और `/* */` दोनों ट्रेलिंग कमेंट के रूप में काम करते हैं, लेकिन `/*` के साथ हमेशा सुनिश्चित करें कि `*/` वहाँ मौजूद हो।

---

Java में एक ब्लॉक कमेंट के अंदर दूसरा ब्लॉक कमेंट नहीं आ सकता, लेकिन Kotlin में वे **नेस्ट** हो सकते हैं: हर `/*` का अपना मेल `*/` से होना चाहिए, और कमेंट केवल तब समाप्त होता है जब सबसे बाहरी वाला बंद हो जाए।
```kotlin
/* outer /* inner */ still a comment */
println("done")
```
यहाँ `still a comment */` बाहरी कमेंट का हिस्सा है, इसलिए केवल `done` ही प्रिंट होता है। यही चीज़ आपको पूरे कोड ब्लॉक को कमेंट आउट करने देती है, तब भी जब उस ब्लॉक में पहले से कोई `/* */` कमेंट मौजूद हो।

---

एक साथ कई लाइनें कमेंट आउट करने के लिए, हर लाइन में `//` जोड़ने के बजाय उन्हें एक ही ब्लॉक कमेंट में लपेटें:
```kotlin
var total = 100
/*
total = total - 30
total = total - 20
*/
println(total) // prints 100
```
नेस्टिंग की बदौलत, यह तब भी काम करता है जब उन लाइनों में से किसी एक में पहले से कोई `/* */` कमेंट मौजूद हो।

---

ब्लॉक कमेंट का एक सामान्य उपयोग **हेडर कमेंट** है: फ़ंक्शन के ठीक ऊपर रखा गया एक छोटा ब्लॉक, जो बताता है कि वह क्या करता है और उसके पैरामीटर का क्या अर्थ है।
```kotlin
/*
Returns the number of seconds in the given minutes.
minutes is a whole number, never negative.
*/
fun toSeconds(minutes: Int): Int {
    return minutes * 60
}
```
अब `toSeconds` को कॉल करने वाला कोई भी व्यक्ति बॉडी की जगह हेडर पढ़ सकता है। हेडर को फ़ंक्शन के पास ही रखें ताकि दोनों एक साथ अपडेट हों।

---

Kotlin में कमेंट की तीसरी किस्म है, **डॉक्युमेंटेशन कमेंट**, जो **KDoc** नाम के फ़ॉर्मेट में लिखा जाता है: यह `/**` (एक स्लैश और दो एस्टरिस्क) से शुरू होकर `*/` पर समाप्त होता है, और इसे फ़ंक्शन, क्लास या प्रॉपर्टी के ठीक ऊपर रखा जाता है।
```kotlin
/**
 * Returns the greeting for [name].
 */
fun greet(name: String): String {
    return "Hi, $name!"
}
```
कंपाइलर के लिए तो यह बस एक कमेंट है, लेकिन IntelliJ IDEA जैसे टूल इसे पढ़ते हैं और `greet` की सहायता सामग्री के रूप में दिखाते हैं। अंदरूनी लाइनों की शुरुआत में लगा `*` केवल एक परंपरा है जो ब्लॉक को सीधा रखती है। KDoc के अंदर आप Markdown का उपयोग कर सकते हैं, और `[name]` जैसे वर्गाकार कोष्ठक उस पैरामीटर के लिंक बन जाते हैं।

---

डॉक्युमेंटेशन कमेंट की पहली लाइन **समरी** होती है: एक छोटा वाक्य जो बताता है कि फ़ंक्शन क्या करता है। इसे तीसरे पुरुष में लिखें, मानो फ़ंक्शन का वर्णन कर रहे हों: "Returns...", "Adds...", "Checks..."।
```kotlin
/**
 * Returns `true` when [n] is divisible by two.
 */
fun isEven(n: Int): Boolean {
    return n % 2 == 0
}
```
कमेंट घोषणा के ठीक ऊपर होना चाहिए, बीच में कोई और कथन नहीं, अन्यथा टूल उसे फ़ंक्शन से नहीं जोड़ते।

---

समरी के बाद, एक डॉक्युमेंटेशन कमेंट **KDoc टैग** के साथ पैरामीटर और लौटाए गए मान का वर्णन कर सकता है, जो हमेशा `@` से शुरू होते हैं:
```kotlin
/**
 * Returns the number of seconds in the given minutes.
 * @param minutes a whole number of minutes, never negative
 * @return [minutes] multiplied by sixty
 */
fun toSeconds(minutes: Int): Int {
    return minutes * 60
}
```
`@param` के बाद पैरामीटर का नाम और फिर उसका विवरण आता है; हर पैरामीटर का अपना एक `@param` होता है। `@return` फ़ंक्शन द्वारा लौटाए गए मान का वर्णन करता है। क्रम हमेशा वही रहता है: पहले समरी, फिर `@param` टैग, फिर `@return`।

---

एक से अधिक पैरामीटर वाले फ़ंक्शन को उनमें से हर एक के लिए एक `@param` टैग मिलता है, जो पैरामीटर के उसी क्रम में लिखे जाते हैं:
```kotlin
/**
 * Returns the area of a rectangle.
 * @param width the horizontal side, in centimetres
 * @param height the vertical side, in centimetres
 * @return the product of [width] and [height]
 */
fun area(width: Int, height: Int): Int {
    return width * height
}
```
एक टैग फिर भी केवल एक कमेंट है: यदि आप किसी पैरामीटर का नाम बदल दें और टैग को अपडेट करना भूल जाएँ, तो कुछ नहीं टूटता, लेकिन दस्तावेज़ीकरण झूठ बोलना शुरू कर देता है। KDoc को सिग्नेचर के साथ एक साथ अपडेट करें।

---

कंपाइलर कमेंट केवल कोड में ढूंढता है, कभी भी **स्ट्रिंग लिटरल** के अंदर नहीं। दोहरे उद्धरण चिह्नों के बीच `//` और `/* */` साधारण अक्षर होते हैं:
```kotlin
println("50 // 2") // prints 50 // 2
```
पहला `//` टेक्स्ट का हिस्सा है, दूसरा एक असली कमेंट शुरू करता है। यह लोगों को सबसे अधिक वेब पतों के साथ चौंकाता है, जिनमें प्रोटोकॉल के ठीक बाद `//` आता है।

---

कुछ कमेंट एक ऐसी परंपरा का पालन करते हैं जिसे एडिटर समझते हैं। सबसे सामान्य **मार्कर** हैं:
- `// TODO: ...` उस चीज़ को दर्शाता है जिसे अभी भी लिखना बाकी है
- `// FIXME: ...` उस कोड को दर्शाता है जो गलत होना ज्ञात है और जिसे ठीक करना ज़रूरी है

```kotlin
val limit = 10
// TODO: read the limit from the settings
```
कंपाइलर के लिए वे साधारण कमेंट हैं; IntelliJ IDEA उन्हें एक समर्पित टूल विंडो में इकट्ठा करता है ताकि बाकी बचा काम ढूंढना आसान हो। एक `TODO` आमतौर पर ऐसे प्लेसहोल्डर के पास रहता है जो असली इम्प्लीमेंटेशन लिखे जाने तक कोड को कंपाइल होते रखता है। जब काम पूरा कर लें, तो उसी बदलाव में प्लेसहोल्डर बदलें और मार्कर हटा दें, ताकि कमेंट कोड की स्थिति के बारे में कभी झूठ न बोले।

---

एक `FIXME` एक `TODO` से अलग है: कोड पहले से मौजूद है, लेकिन वह गलत होना ज्ञात है। एक अच्छा `FIXME` बताता है कि बग क्या है और, जहाँ संभव हो, उसे दिखाने वाला एक उदाहरण देता है, ताकि अगला व्यक्ति उसे जल्दी ठीक कर सके। `TODO` की तरह, बग ठीक होते ही मार्कर हटा दें, लेकिन डॉक्युमेंटेशन कमेंट रखें, जो अभी भी सही है।

---

एक अच्छा कमेंट यह बताता है कि कोड कुछ **क्यों** करता है, यह नहीं कि वह **क्या** करता है। कोड पहले से दिखा देता है कि क्या होता है; उसे शब्दों में दोहराना केवल शोर जोड़ता है और जैसे ही कोड बदलता है, वह पुराना पड़ जाता है:
```kotlin
// set timeout to 30
val timeout = 30
```
संख्या के पीछे का कारण ही वह चीज़ है जिसका अंदाज़ा पाठक नहीं लगा सकता:
```kotlin
// the server drops idle connections after 35 seconds, so stop earlier
val timeout = 30
```
यदि कोई कमेंट केवल अपने नीचे की लाइन को दोहराता है, तो उसे हटा दें या कारण से बदल दें। सबसे अच्छे कमेंट वे होते हैं जो कुछ ऐसा बताते हैं जो कोड नहीं बता सकता।

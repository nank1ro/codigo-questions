Swift में एक एरर एक **मान** होता है, क्रैश नहीं। कोई भी टाइप `Error` प्रोटोकॉल को अपनाकर एरर की भूमिका निभा सकता है, और enum आमतौर पर इसके लिए इस्तेमाल होने वाला विकल्प है क्योंकि इसके cases ठीक-ठीक बताते हैं कि क्या गलत हो सकता है:
```swift
enum LoginError: Error {
    case wrongPassword
}
```
विफल हो सकने वाले फ़ंक्शन को `throws` से चिह्नित किया जाता है, और यह `throw` के साथ विफलता की रिपोर्ट करता है:
```swift
func login(_ password: String) throws {
    if password != "swift" {
        throw LoginError.wrongPassword
    }
    print("welcome")
}
```
ऐसे फ़ंक्शन को कॉल करने के लिए `try` चाहिए, और यह कॉल एक `do` ब्लॉक के अंदर होनी चाहिए जिसके बाद एक `catch` ब्लॉक आता है जो बताता है कि विफल होने पर क्या करना है:
```swift
do {
    try login("hunter2")
} catch {
    print("login failed")
}
// login failed
```
जब `throw` चलता है, तो `do` ब्लॉक का बाकी हिस्सा छोड़ दिया जाता है और `catch` संभाल लेता है। कुछ भी क्रैश नहीं होता: प्रोग्राम `catch` के बाद आगे बढ़ता रहता है।

---

थ्रो करने वाला फ़ंक्शन अभी भी एक मान लौटा सकता है। `throws` कीवर्ड पैरामीटर लिस्ट और रिटर्न ऐरो के बीच आता है:
```swift
func square(_ n: Int) throws -> Int {
    if n < 0 {
        throw SquareError.negative
    }
    return n * n
}
```
इसे ज़ोर से पढ़ें तो: *square एक `Int` लेता है, हो सकता है थ्रो करे, और एक `Int` लौटाता है*।

कॉल साइट पर यह मान तभी मौजूद होता है जब कुछ भी थ्रो नहीं हुआ हो, इसलिए असाइनमेंट `do` ब्लॉक के अंदर रहता है:
```swift
do {
    let result = try square(4)
    print(result) // 16
} catch {
    print("failed")
}
```
`try` कोई वैकल्पिक सजावट नहीं है: इसके बिना कंपाइलर कॉल को अस्वीकार कर देता है, ताकि पढ़ने वाले को हमेशा दिखे कि कौन सी लाइनें विफल हो सकती हैं।

---

एक बिना पैटर्न वाला `catch` हर एरर को एक ही तरह संभालता है। ज़्यादातर समय आप किसी एक खास विफलता पर प्रतिक्रिया देना चाहते हैं, इसलिए एक `catch` एक **पैटर्न** रख सकता है: वह case जिसे वह संभालने को तैयार है।
```swift
do {
    try check("")
} catch ValidationError.empty {
    print("the text is empty")
} catch {
    print("something else")
}
```
Swift `catch` क्लॉज़ेज़ को ऊपर से नीचे तक आज़माता है और पहला वही चलाता है जिसका पैटर्न मैच हो जाता है।

आख़िरी `catch` में जानबूझकर कोई पैटर्न नहीं है। एक पैटर्न वाला `catch` केवल उसी case को कवर करता है जिसका नाम वह लेता है, और Swift चाहता है कि हर एरर कहीं न कहीं संभाला जाए, इसलिए पैटर्न लिस्ट करने वाले `do` ब्लॉक को बाकी बचे सब को समेटने के लिए अंत में एक बिना पैटर्न वाले `catch` की ज़रूरत होती है।

---

क्रम मायने रखता है। Swift थ्रो किए गए मान की तुलना हर `catch` पैटर्न से उसी क्रम में करता है जिस क्रम में वे लिखे गए हैं और पहले मैच पर रुक जाता है, इसलिए सबसे पहले रखा गया बिना पैटर्न वाला `catch` उसके नीचे के सब कुछ निगल जाएगा। विशिष्ट cases को सबसे ऊपर और catch-all को सबसे नीचे रखें।

जो एरर किसी भी पैटर्न से मैच नहीं होता, वह नज़रअंदाज़ नहीं किया जाता: वह अंतिम बिना पैटर्न वाले `catch` में जाता है।

---

एक एरर case डेटा रख सकता है। case को **एसोसिएटेड वैल्यूज़** दें और `throw` उन्हें भर देता है, ताकि हैंडलर को सिर्फ़ यह नहीं पता चले कि *क्या* विफल हुआ, बल्कि *कितना* भी:
```swift
enum ValidationError: Error {
    case tooShort(minimum: Int)
}

throw ValidationError.tooShort(minimum: 8)
```
मैच होने वाला `catch` उन मानों को `let` के साथ बाइंड करता है:
```swift
} catch ValidationError.tooShort(let minimum) {
    print("needs at least \(minimum) characters")
}
```
`let` के बाद दिया गया नाम आपकी पसंद का है; यह एक नया कॉन्स्टेंट है जो केवल उसी `catch` ब्लॉक के अंदर उपलब्ध है। इसी तरह एक एरर एक उपयोगी संदेश रखता है, बिना यह ज़रूरत के कि आप विफलता होने की जगह पर स्ट्रिंग्स में संख्याएँ पेस्ट करें।

---

आमतौर पर एक ही enum में एक काम के विफल होने के सभी तरीके होते हैं, हर कारण के लिए एक case:
```swift
enum FormError: Error {
    case empty
    case tooLong
}
```
हर case के लिए अलग `catch` लिखना दोहराव भरा हो जाता है। इसके बजाय, पूरे टाइप को एक साथ कैच करें और मान पर `switch` करें:
```swift
} catch let error as FormError {
    switch error {
    case .empty: print("empty")
    case .tooLong: print("too long")
    }
} catch {
    print("unknown")
}
```
`catch let error as FormError` का मतलब है *जो कुछ भी `FormError` है उसे कैच करें, और उसे `error` कहें*। ब्लॉक के अंदर `error` का टाइप enum है, इसलिए `switch` को cases दिखते हैं और वह जाँचता है कि आपने उन सबको कवर किया है। अंतिम बिना पैटर्न वाला `catch` फिर भी ज़रूरी है, क्योंकि कोई दूसरे टाइप का एरर इस `do` ब्लॉक तक पहुँच सकता है।

---

एक वैलिडेटर सबसे अच्छा पढ़ा जाता है जब अस्वीकृतियाँ पहले आती हैं और असली काम नीचे बिना इंडेंट के रह जाता है। `guard` इसी के लिए बना है: यह उस शर्त को बताता है जो पूरी होनी चाहिए, और शर्त पूरी न होने पर इसका `else` ब्लॉक चलता है।
```swift
func priceFor(_ quantity: Int) throws -> Int {
    guard quantity > 0 else {
        throw OrderError.notPositive
    }
    return quantity * 3
}
```
`guard` के `else` ब्लॉक को मौजूदा स्कोप छोड़ना ही होता है, और `throw` उसके तरीकों में से एक है, `return`, `break` और `continue` की तरह। फ़ंक्शन के शुरू में एक के ऊपर एक लगे कई `guard` इनपुट पर लागू होने वाले नियमों की सूची जैसे पढ़े जाते हैं।

---

कभी-कभी आपको यह परवाह नहीं होती कि कोई चीज़ *क्यों* विफल हुई, सिर्फ़ इतना कि वह विफल हुई। `try?` एक थ्रो करने वाली कॉल को एक **ऑप्शनल** में बदल देता है: सफल होने पर मान, थ्रो करने पर `nil`।
```swift
enum ParseError: Error {
    case notANumber
}

func toInt(_ text: String) throws -> Int {
    guard let value = Int(text) else {
        throw ParseError.notANumber
    }
    return value
}

if let number = try? toInt("42") {
    print(number) // 42
}
```
न `do`, न `catch`: विफलता उसी ऑप्शनल में समा जाती है जिसे अनरैप करना आप पहले से जानते हैं। कीमत यह है कि एरर का मान फेंक दिया जाता है, इसलिए `try?` का उपयोग तभी करें जब सच में रिपोर्ट करने को कुछ न हो।

---

चूँकि `try?` एक ऑप्शनल बनाता है, nil-coalescing ऑपरेटर `??` एक फॉलबैक देकर काम पूरा कर देता है:
```swift
let port = (try? readPort(text)) ?? 8080
```
कोष्ठक मायने रखते हैं। अन्यथा `try?` पूरे एक्सप्रेशन को `??` समेत कवर करने की कोशिश करता, और कंपाइलर आपसे यह स्पष्ट करने को कहता है कि विफल होने वाली कॉल कहाँ खत्म होती है।

इस लाइन को एक वाक्य की तरह पढ़ें: *जो पोर्ट पढ़ने में सफल रहे उसका उपयोग करें, अन्यथा 8080*। जब रिकवरी वास्तव में सिर्फ़ एक डिफ़ॉल्ट मान हो, तो `do`/`catch` की दो लाइनें एक में बदल जाती हैं।

---

तीसरा रूप भी है: `try!`। यह कंपाइलर को बताता है *यह कॉल विफल नहीं हो सकती*, इसलिए न कोई `do`, न `catch` और न कोई ऑप्शनल। अगर वह फिर भी विफल हो जाए, तो प्रोग्राम तुरंत रुक जाता है।
```swift
let pattern = try! Regex("[0-9]+")
```
यही वह आकार है जहाँ `try!` जायज़ है: आर्ग्युमेंट आपके द्वारा, अपने ही सोर्स में लिखा गया एक literal है, और अगर वह गलत है तो प्रोग्राम टूटा हुआ है और उसे आपकी पहली टेस्ट रन के दौरान ही रुक जाना चाहिए।

रनटाइम पर आने वाली कोई भी चीज़ — उपयोगकर्ता द्वारा टाइप की गई लाइन, एक फ़ाइल, नेटवर्क रिस्पॉन्स — उन तरीकों से गलत हो सकती है जो कोड लिखते समय आपको दिख नहीं सकते, और उस पर `try!` लगाने से ठीक की जा सकने वाली विफलता उपयोगकर्ता के सामने क्रैश में बदल जाती है। वहाँ `do`/`catch` या `try?` का उपयोग करें।

---

जब कोई फ़ंक्शन थ्रो करता है, तो `throw` के बाद की हर चीज़ छोड़ दी जाती है — फ़ाइल बंद करने या लॉक छोड़ने वाली लाइन समेत। `defer` इसका समाधान है: यह एक ब्लॉक अभी रजिस्टर करता है और मौजूदा स्कोप के खत्म होने पर चलाता है, चाहे वह किसी भी तरह खत्म हो।
```swift
func load() throws {
    print("open")
    defer { print("close") }
    throw FileError.missing
}
```
कॉल करने पर `open` प्रिंट होता है, फिर `close`, और उसके बाद ही एरर कॉलर की ओर बढ़ता है। अगर फ़ंक्शन सामान्य तरीके से लौटता, तब भी `close` प्रिंट होता — यही तो बात है। क्लीनअप को सेटअप के ठीक बगल में रखें और इस बात की चिंता छोड़ दें कि कोड किस रास्ते बाहर निकलेगा।

---

एक स्कोप एक से अधिक `defer` रजिस्टर कर सकता है। वे **उल्टे** क्रम में चलते हैं: सबसे बाद में रजिस्टर हुआ सबसे पहले चलता है।

यह कोई मनमाना नियम नहीं है। क्लीनअप आमतौर पर क्रम में हुए सेटअप को वापस करते हैं — फ़ाइल खोलें, फिर उसे लॉक करें — और वापस करना उल्टी दिशा में जाना ही चाहिए: अनलॉक करें, फिर बंद करें। उल्टा क्रम हर `defer` को उसके ऊपर की लाइन का दर्पण प्रतिबिंब बना देता है।

---

क्लोजर लेने वाले फ़ंक्शन की एक समस्या होती है: वह नहीं जान सकता कि उसे दिया गया क्लोजर थ्रो करेगा या नहीं। फ़ंक्शन को `throws` चिह्नित करने से हर कॉल करने वाले को `try` लिखना पड़ता, यहाँ तक कि जो बेक़सूर क्लोजर पास कर रहे हों उन्हें भी। `rethrows` कहता है *मैं तभी थ्रो करूँगा जब आपके दिया क्लोजर थ्रो करे*:
```swift
func applyTwice(_ value: Int, _ transform: (Int) throws -> Int) rethrows -> Int {
    return try transform(transform(value))
}
```
बॉडी के अंदर आप फिर भी `try` लिखते हैं, क्योंकि यह कॉल सच में विफल हो सकती है। कॉल साइट पर कंपाइलर आपके पास किए गए क्लोजर को देखता है:
```swift
let doubled = applyTwice(3, { (n: Int) -> Int in n * 2 }) // try की ज़रूरत नहीं है
```
स्टैंडर्ड लाइब्रेरी इसे हर जगह उपयोग करती है — `map`, `filter` और `sorted(by:)` सब `rethrows` हैं — इसीलिए आप कभी किसी साधारण `map` के आगे `try` नहीं लिखते।

---

एक `do` ब्लॉक केवल एक ही एरर टाइप तक सीमित नहीं है। हर कदम अपने तरीके से विफल हो सकता है, और हर विफलता का अपना `catch` बनता है:
```swift
do {
    let text = try load(false)
    let value = try parse(text)
    print(value)
} catch NetworkError.offline {
    print("offline")
} catch ParseError.badFormat {
    print("bad format")
} catch {
    print("unknown")
}
```
थ्रो करने वाला पहला `try` ब्लॉक को खत्म कर देता है, इसलिए बाद के कदम कभी नहीं चलते — वह मान कभी मौजूद ही नहीं होता। यही इस आकार को पढ़ने में आसान बनाता है: सफल पाथ ऊपर एक सीधी लाइन में रहता है, और गलत होने का हर संभावित तरीका नीचे सूचीबद्ध रहता है।

एक **प्रोटोकॉल** बताता है कि किसी टाइप में क्या होना चाहिए, यह बताए बिना कि कैसे। यह आवश्यकताओं — प्रॉपर्टीज़ और मेथड्स — की एक सूची है जिसे देने का वादा उसे अपनाने वाला कोई भी टाइप करता है।

आप इसे `protocol` कीवर्ड से घोषित करते हैं। एक प्रॉपर्टी आवश्यकता उसके टाइप के साथ लिखी जाती है, जिसके बाद एक ब्लॉक होता है जो बताता है कि उसे कैसे एक्सेस किया जा सकता है: `{ get }` का मतलब है कि टाइप कम से कम आपको उसे पढ़ने दे।
```swift
protocol Named {
    var name: String { get }
}
```
कोई टाइप प्रोटोकॉल के **अनुरूप** बनता है, प्रोटोकॉल के नाम को कोलन के बाद लिखकर और प्रोटोकॉल द्वारा माँगी गई हर चीज़ देकर:
```swift
struct Cat: Named {
    var name: String
}

let cat = Cat(name: "Luna")
print(cat.name) // Luna
```
प्रोटोकॉल अपना कोई डेटा नहीं रखता: यह एक अनुबंध है। जो भी टाइप इसे पूरा करता है, आपके बाकी कोड उसके साथ एक जैसा व्यवहार कर सकता है।

---

एक प्रोटोकॉल **मेथड्स** की आवश्यकता भी रख सकता है। आप सिग्नेचर — नाम, पैरामीटर्स और रिटर्न टाइप — लिखते हैं और वहीं रुक जाते हैं, बिना बॉडी के:
```swift
protocol Greeter {
    func greet() -> String
}
```
अनुरूप बनने वाले टाइप को बिल्कुल उसी सिग्नेचर वाली मेथड घोषित करनी होती है, और बॉडी वह देता है:
```swift
struct Robot: Greeter {
    func greet() -> String {
        return "BEEP"
    }
}

print(Robot().greet()) // BEEP
```
अगर कुछ भी अलग हो — नाम, कोई पैरामीटर टाइप या रिटर्न टाइप — तो टाइप अनुरूप नहीं बनता, और कंपाइलर बताता है कि कौन सी आवश्यकता पूरी नहीं हुई।

---

एक प्रॉपर्टी आवश्यकता हमेशा बताती है कि प्रॉपर्टी का उपयोग कैसे किया जा सकता है। `{ get }` केवल इतना माँगता है कि मान पढ़ा जा सके; `{ get set }` माँगता है कि उसे पढ़ा **और** असाइन किया जा सके:
```swift
protocol Account {
    var owner: String { get }
    var balance: Int { get set }
}
```
अनुरूप बनने वाला टाइप हमेशा अनुबंध से ज़्यादा दे सकता है: एक `var` स्टोर्ड प्रॉपर्टी `{ get }` को पूरी तरह संतुष्ट करती है। यह कभी कम नहीं दे सकता — एक `let` कॉन्स्टेंट, या रीड-ओनली कंप्यूटेड प्रॉपर्टी, `{ get set }` को पूरा नहीं कर सकती।

---

प्रोटोकॉल केवल स्ट्रक्चर्स तक सीमित नहीं हैं। एक **क्लास** बिल्कुल उसी तरह अनुरूप बनता है, कोलन के बाद प्रोटोकॉल को सूचीबद्ध करके:
```swift
protocol Openable {
    func open() -> String
}

class Door: Openable {
    func open() -> String {
        return "creak"
    }
}
```
अगर क्लास किसी दूसरी क्लास से भी इनहेरिट करती है, तो सुपरक्लास सूची में पहले आता है और प्रोटोकॉल उसके बाद। एक टाइप कई प्रोटोकॉल एक साथ अपना सकता है, कोमा से अलग करके।

---

एक **एनम** भी अनुरूप बन सकता है। उसके पास कोई स्टोर्ड प्रॉपर्टीज़ नहीं होतीं, इसलिए प्रॉपर्टी आवश्यकता आमतौर पर एक कंप्यूटेड प्रॉपर्टी से पूरी की जाती है जो केसेस पर स्विच करती है:
```swift
protocol Priced {
    var price: Int { get }
}

enum Ticket: Priced {
    case child, adult

    var price: Int {
        switch self {
        case .child: return 5
        case .adult: return 12
        }
    }
}

print(Ticket.adult.price) // 12
```
स्ट्रक्चर्स, क्लासेस और एनम: ये तीनों प्रोटोकॉल को एक ही तरह से अपनाते हैं, और प्रोटोकॉल के आधार पर लिखा गया कोड तीनों के साथ काम करता है।

---

एक प्रोटोकॉल आमतौर पर एक से अधिक आवश्यकताएँ रखता है, और अनुरूप बनने वाले टाइप को उनमें से हर एक को पूरा करना होता है:
```swift
protocol Vehicle {
    var wheels: Int { get }
    func move() -> String
}

struct Bike: Vehicle {
    var wheels = 2

    func move() -> String {
        return "pedalling"
    }
}
```
ब्रेसेस के अंदर आवश्यकताओं का क्रम मायने नहीं रखता, और न ही उस क्रम का जिसमें अनुरूप बनने वाला टाइप उन्हें देता है: कंपाइलर केवल यह जाँचता है कि कुछ भी मिसिंग न हो।

---

एक स्ट्रक्चर एक वैल्यू टाइप होता है, इसलिए अपनी किसी स्टोर्ड प्रॉपर्टी को बदलने वाली मेथड को `mutating` के रूप में मार्क किया जाना चाहिए। जब वही मेथड किसी प्रोटोकॉल की आवश्यकता हो, तो प्रोटोकॉल को भी यह कहना होता है:
```swift
protocol Togglable {
    mutating func toggle()
}

struct Light: Togglable {
    var isOn = false

    mutating func toggle() {
        isOn = !isOn
    }
}

var lamp = Light()
lamp.toggle()
print(lamp.isOn) // true
```
प्रोटोकॉल में `mutating` के बिना, कोई स्ट्रक्चर कभी भी इस आवश्यकता को पूरा नहीं कर सकता। क्लासेस रेफरेंस टाइप्स होते हैं और उन्हें इस कीवर्ड की ज़रूरत कभी नहीं होती: कोई क्लास `mutating` आवश्यकता को एक साधारण मेथड से पूरा करता है। म्यूटेटिंग मेथड कॉल करने के लिए एक `var` चाहिए — `let` पर यह एक कंपाइल एरर है।

---

अनुरूपता को टाइप के बगल में घोषित करना ज़रूरी नहीं है। एक **एक्सटेंशन** इसे बाद में जोड़ सकता है, जिससे टाइप की अपनी डिक्लेरेशन अपने डेटा पर केंद्रित रहती है:
```swift
protocol Resettable {
    mutating func reset()
}

struct Timer {
    var seconds = 0
}

extension Timer: Resettable {
    mutating func reset() {
        seconds = 0
    }
}
```
यह उन टाइप्स के लिए भी काम करता है जिन्हें आपने नहीं लिखा: आप किसी स्टैंडर्ड लाइब्रेरी टाइप को बिना उसके सोर्स को छुए अपने किसी प्रोटोकॉल के अनुरूप बना सकते हैं।

---

एक **प्रोटोकॉल** का एक्सटेंशन एक अलग टूल है: यह हर अनुरूप बनने वाले टाइप — मौजूदा और भविष्य के — में मेंबर्स जोड़ता है। किसी आवश्यकता को **डिफ़ॉल्ट इंप्लीमेंटेशन** देने का तरीका यही है:
```swift
protocol Greeter {
    var name: String { get }
    func greet() -> String
}

extension Greeter {
    func greet() -> String {
        return "Hi, \(name)"
    }
}

struct Person: Greeter {
    var name: String
}

print(Person(name: "Ada").greet()) // Hi, Ada
```
`Person` कभी `greet()` नहीं लिखता और फिर भी अनुरूप बना रहता है। प्रोटोकॉल एक्सटेंशन के अंदर आप प्रोटोकॉल की हर आवश्यकता का उपयोग कर सकते हैं — यहाँ `name` — क्योंकि अनुरूप बनने वाले किसी भी टाइप में उसके होने की गारंटी होती है।

---

एक प्रोटोकॉल एक्सटेंशन ऐसे मेंबर्स भी जोड़ सकता है जिन्हें प्रोटोकॉल ने कभी आवश्यकता के रूप में सूचीबद्ध नहीं किया। ये अतिरिक्त सुविधाएँ हैं, जो हर अनुरूप बनने वाले टाइप पर उपलब्ध हैं:
```swift
protocol Sized {
    var count: Int { get }
}

extension Sized {
    var isEmpty: Bool {
        return count == 0
    }
}
```
`isEmpty` कोई आवश्यकता नहीं है, इसलिए अनुरूप बनने वाले टाइप को उसे देने की ज़रूरत नहीं — उसे वह बस मिल जाता है।

---

एक प्रोटोकॉल दूसरे पर बन सकता है। कोलन के बाद किसी प्रोटोकॉल का नाम लिखने से नया प्रोटोकॉल पुराने की हर आवश्यकता को **इनहेरिट** करता है:
```swift
protocol Named {
    var name: String { get }
}

protocol Aged: Named {
    var age: Int { get }
}
```
`Aged` के अनुरूप बनने वाले टाइप को `age` *और* `name` दोनों देने होते हैं, और वह हर जगह एक `Named` टाइप की तरह गिना जाता है। एक प्रोटोकॉल कई प्रोटोकॉल से एक साथ इनहेरिट कर सकता है, कोमा से अलग करके।

---

डिफ़ॉल्ट इंप्लीमेंटेशन एक फॉलबैक है, कोई नियम नहीं। अगर अनुरूप बनने वाला टाइप किसी आवश्यकता का अपना वर्ज़न देता है, तो वही वर्ज़न चलता है:
```swift
protocol Priced {
    var price: Int { get }
}

extension Priced {
    var price: Int { return 0 }
}

struct Ticket: Priced {
    var price = 12
}

print(Ticket().price) // 12, न कि 0
```
डिफ़ॉल्ट केवल वही गैप भरता है जिन्हें टाइप खुला छोड़ देता है।

---

स्टैंडर्ड लाइब्रेरी प्रोटोकॉल्स से बनी है, और आपके अपने टाइप्स उन्हें अपना सकते हैं।

`Equatable` किसी टाइप को `==` ऑपरेटर देता है। उस स्ट्रक्चर के लिए जिसकी सभी स्टोर्ड प्रॉपर्टीज़ `Equatable` हैं, अनुरूपता घोषित करना ही काफी है — Swift आपके लिए `==` लिख देता है:
```swift
struct Point: Equatable {
    var x: Int
    var y: Int
}

print(Point(x: 1, y: 2) == Point(x: 1, y: 2)) // true
```
`Comparable` `Equatable` से इनहेरिट करता है और ऑर्डरिंग जोड़ता है। आप एक अकेला ऑपरेटर `<` इंप्लीमेंट करते हैं, जो दो मान लेने वाले `static func` के रूप में लिखा जाता है, और आपको `>`, `<=`, `>=`, साथ ही कलेक्शन्स पर `sorted()`, `min()` और `max()` मुफ़्त में मिल जाते हैं:
```swift
struct Version: Comparable {
    var number: Int

    static func < (lhs: Version, rhs: Version) -> Bool {
        return lhs.number < rhs.number
    }
}
```

---

`CustomStringConvertible` तय करता है कि `print` आपके टाइप के लिए क्या दिखाए। उसकी एक अकेली आवश्यकता एक `description` प्रॉपर्टी है:
```swift
struct Coin: CustomStringConvertible {
    var value: Int

    var description: String {
        return "\(value)c"
    }
}

print(Coin(value: 25)) // 25c
```
अनुरूपता के बिना, किसी स्ट्रक्चर को प्रिंट करने पर `Coin(value: 25)` जैसा एक डिफ़ॉल्ट डंप दिखता है, और अकेली `description` प्रॉपर्टी कुछ नहीं बदलती — `print` प्रोटोकॉल की तलाश करता है। स्ट्रिंग इंटरपोलेशन भी `description` का उपयोग करता है।

---

अकेला प्रोटोकॉल नाम एक टाइप नहीं है, वह एक कॉन्स्ट्रेंट है, इसलिए Swift आपसे कहता है कि आप दो चीज़ों में से किसका मतलब रखते हैं।

`some Shape` का मतलब है *एक विशिष्ट अनुरूप टाइप*, जो कंपाइल टाइम पर तय होता है। कॉलर को कभी पता नहीं चलता कि कौन सा, लेकिन वह हमेशा एक ही होता है:
```swift
func unitSquare() -> some Shape {
    return Square(side: 1)
}
```
`any Shape` का मतलब है *एक बॉक्स जो कोई भी अनुरूप टाइप रख सकता है*, और उस टाइप के दो मान अलग-अलग टाइप्स रख सकते हैं। इसकी ज़रूरत तब होती है जब कंक्रीट टाइप बदल सकता हो, जैसे एक मिक्स्ड ऐरे के अंदर:
```swift
let shapes: [any Shape] = [Square(side: 2), Rect(width: 2, height: 3)]
```
दोनों आपको प्रोटोकॉल की आवश्यकताओं को कॉल करने देते हैं। जब एक अकेला टाइप काफी हो तो `some` को प्राथमिकता दें, क्योंकि उसकी रन टाइम पर कोई लागत नहीं होती; `any` का उपयोग तब करें जब आपको सचमुच टाइप्स मिलाने की ज़रूरत हो।

कुछ कथन पूरे नहीं किए जा सकते: ऐसा टेक्स्ट पढ़ना जो संख्या नहीं है, सूची के अंत से आगे कोई तत्व लेना, खाली सूची से पहला आइटम माँगना। ऐसा होने पर Dart विफलता का वर्णन करने वाली एक वस्तु **फेंकता** है।

आप स्वयं `throw` कीवर्ड से ऐसी वस्तु फेंक सकते हैं। `Exception('message')` एक छोटी व्याख्या ले जाने वाली तैयार वस्तु बनाता है:

```dart
throw Exception('no fuel');
```

फेंकना कोई `return` नहीं है। वह कथन, फंक्शन और ऊपर के हर कॉलर को छोड़ देता है और उसे संभालने वाली किसी चीज़ को खोजता है। जब कोई उसे नहीं पकड़ता, तो प्रोग्राम रुक जाता है और विफलता प्रिंट करता है:

```
Unhandled exception:
Exception: no fuel
```

फेंके जाने के बाद की हर चीज़ छोड़ दी जाती है, इसलिए जो पंक्तियाँ चलतीं वे कभी नहीं चलतीं। यही इस टॉपिक का विषय है: प्रोग्राम का अंत करने देने के बजाय तय करना कि विफलता कहाँ संभाली जाए।

---

प्रोग्राम को चलते रखने के लिए जोखिम भरे कथन को एक `try` ब्लॉक में लपेटें और रिकवरी का वर्णन एक `catch` ब्लॉक में करें:

```dart
try {
  print(int.parse('twelve'));
} catch (e) {
  print('that is not a number');
}
```

`int.parse` तब फेंकता है जब टेक्स्ट कोई पूर्ण संख्या न दर्शाता हो। Dart पहले उस कथन पर `try` ब्लॉक छोड़ देता है जो फेंकता है, उसका बाकी हिस्सा छोड़ देता है, `catch` ब्लॉक चलाता है, और फिर आगे वाले कोड से चलना जारी रखता है। कोष्ठकों में रखा वेरिएबल, यहाँ `e`, स्वयं फेंकी गई वस्तु है।

`try` ब्लॉक के अंदर से कुछ भी वापस नहीं किया जाता, इसलिए उसे उतना ही छोटा रखें जितनी विफलता की आप अपेक्षा करते हैं।

---

एक खाली `catch` सब कुछ पकड़ लेता है, जिन विफलताओं की आपने योजना नहीं बनाई उन्हें भी छिपा देता है। ठीक एक ही प्रकार संभालने के लिए उसका टाइप एक `on` क्लॉज़ में लिखें:

```dart
try {
  return int.parse(text);
} on FormatException catch (e) {
  return -1;
}
```

`int.parse` तब एक **`FormatException`** फेंकता है जब टेक्स्ट कोई पूर्ण संख्या न हो, इसलिए इनपुट पढ़ते समय यही टाइप लिखना है। एक `on` क्लॉज़ उस टाइप और उसके सबटाइप्स से मेल खाता है, और किसी और से नहीं: कोई और विफलता बाहर की ओर यात्रा करती रहती है और फिर भी सामने आ जाती है, बजाय इसके कि उसे कोई ऐसी रिकवरी निगल जाए जो उसके लिए कभी थी ही नहीं।

---

एक `try` ब्लॉक के बाद **कई** क्लॉज़ हो सकते हैं, हर एक किसी अलग विफलता से रिकवर करता हुआ। Dart ऊपर से नीचे तक फेंकी गई वस्तु की उनसे तुलना करता है और जो **पहला** मेल खाता है उसे चलाता है:

```dart
try {
  return names[int.parse(text)];
} on FormatException {
  return 'not a number';
} on RangeError {
  return 'out of range';
} catch (e) {
  return 'unknown problem';
}
```

किसी सूची को ऐसे इंडेक्स से पढ़ना जो मौजूद नहीं है एक **`RangeError`** फेंकता है, इसलिए उस एक पंक्ति की दोनों विफलताओं को अलग-अलग उत्तर मिलते हैं।

चूँकि पहला मेल जीत जाता है, क्रम मायने रखता है: किसी सामान्य टाइप वाला क्लॉज़ किसी अधिक विशिष्ट क्लॉज़ के ऊपर रखा जाए तो हमेशा जीत जाएगा, और विशिष्ट क्लॉज़ अप्राप्य हो जाएगा। विशिष्ट क्लॉज़ पहले लिखें, और अंत में एक खाली `catch` रखें यदि आप सुरक्षा जाल चाहते हैं।

ऊपर वाला `on RangeError` क्लॉज़ यहाँ केवल यह दिखाने के लिए है कि कई क्लॉज़ कैसे क्रमित होते हैं। `RangeError` प्रोग्राम के नियंत्रण से बाहर किसी स्थिति के बजाय कोड में गलती का संकेत देता है, और आगे एक अभ्यास समझाता है कि ऐसी विफलता को पकड़ने के बजाय रोका क्यों जाना चाहिए।

---

अक्सर रिकवरी को फेंकी गई वस्तु की ज़रूरत ही नहीं होती: टाइप पहले से सब कुछ कह देता है। ऐसे में `catch` वाला हिस्सा हटा दें और केवल `on` क्लॉज़ रखें:

```dart
try {
  return int.parse(text);
} on FormatException {
  return 0;
}
```

दोनों रूप केवल इस बात में अलग हैं कि आपको वेरिएबल मिलता है या नहीं:

- `on FormatException catch (e)` — उस टाइप से मेल खाता है और वस्तु आपको `e` के रूप में देता है
- `on FormatException` — उस टाइप से मेल खाता है, कोई वेरिएबल नहीं
- `catch (e)` — सब कुछ से मेल खाता है और वस्तु आपको देता है

अप्रयुक्त वेरिएबल छोड़ देने से हैंडलर ईमानदार रहता है कि वह सचमुच क्या उपयोग करता है।

---

हैंडलरों के बाद एक तीसरा ब्लॉक आ सकता है। `finally` **हर हाल में** चलता है: `try` ब्लॉक के सामान्य रूप से पूरा होने के बाद, किसी हैंडलर के रिकवर करने के बाद, और तब भी जब कुछ भी मेल न खाए और विफलता अभी भी बाहर की ओर यात्रा कर रही हो।

```dart
try {
  return 'parsed ${int.parse(text)}';
} on FormatException {
  return 'failed';
} finally {
  print('done');
}
```

वह `return` के अपना मान लौटाने से पहले भी चलता है, इसीलिए ऊपर वाला संदेश कॉलर के परिणाम देखने से पहले प्रिंट होता है। इसीलिए `finally` उस काम की जगह बन जाता है जो किसी भी हालत में होना चाहिए, जैसे खोली हुई चीज़ बंद करना।

---

आपका अपना कोड उसी तरह फेंकता है जिस तरह लाइब्रेरी करती है। `Exception('message')` एक सादा अपवाद बनाता है जो एक छोटी व्याख्या ले जाता है, और `throw` उसे रवाना कर देता है:

```dart
if (amount > balance) {
  throw Exception('insufficient funds');
}
```

संदेश खोता नहीं है: `toString()` शब्द `Exception`, एक कोलन और संदेश को साथ जोड़ देता है, जो ठीक वही है जो unhandled-exception रिपोर्ट प्रिंट करती है।

```dart
print(Exception('insufficient funds')); // Exception: insufficient funds
```

फेंकना `-1` जैसी बनाई-गई कोई मान लौटाने से बेहतर है: कॉलर उसे देखना भूल नहीं सकता, और कारण उसके साथ ही यात्रा करता है।

---

कभी-कभी हैंडलर रिकवर करने की सही जगह नहीं होती: आप केवल विफलता को *देखना* चाहते हैं और उसे उस कॉलर तक जाने देना चाहते हैं जो वास्तव में उसे संभाल सकता है। `rethrow` कीवर्ड यही करता है, एक `catch` या `on ... catch` ब्लॉक के अंदर:

```dart
try {
  return int.parse(text);
} on FormatException {
  log.add('bad input: $text');
  rethrow;
}
```

`rethrow` **वही** वस्तु आगे भेजता है, इसलिए कॉलर को मूल विफलता दिखती है। इसके बजाय `throw e` लिखना भी चल जाएगा, पर वह यात्रा फिर से शुरू कर देता है और खो देता है कि विफलता पहले कहाँ हुई थी।

उसी कथन का एक `finally` ब्लॉक फिर भी चलता है, बाहर निकलते समय भी।

---

एक `catch` क्लॉज़ एक **दूसरा** पैरामीटर भी लेता है:

```dart
try {
  return int.parse(text);
} on FormatException catch (e, s) {
  log.add('$e');
  log.add('$s');
  rethrow;
}
```

पहला फेंकी गई वस्तु है, दूसरा एक `StackTrace` है: फेंकने के क्षण चल रही कॉलों की श्रृंखला। वह बताता है कि विफलता *कहाँ से* आई, जो अकेला संदेश शायद ही कभी बताता है।

एक स्टैक ट्रेस फ़ाइल नाम, पंक्ति संख्याएँ और फ़्रेम सूचीबद्ध करता है, और वह बिल्ड और कॉल पथ के साथ बदल जाता है। उसे प्रिंट करें, किसी रिपोर्ट से जोड़ें, आगे भेजें — पर उसकी कभी किसी निश्चित टेक्स्ट से तुलना न करें, और उसकी सामग्री पर कभी प्रोग्राम का व्यवहार न बनाएँ। उसे केवल तब माँगें जब आप उसे लॉग करने वाले हों।

---

`Exception` एक इंटरफ़ेस है, इसलिए आपकी अपनी क्लास भी वह हो सकती है। एक कस्टम अपवाद विफलता को वह नाम देता है जिसे एक `on` क्लॉज़ चुन सकता है, और वे फ़ील्ड देता है जिन्हें एक हैंडलर पढ़ सकता है:

```dart
class EmptyCartException implements Exception {
  final String message;

  EmptyCartException(this.message);

  @override
  String toString() => 'EmptyCartException: $message';
}

throw EmptyCartException('nothing to pay for');
```

तीन हिस्से रखने लायक हैं: `implements Exception` ताकि क्लास बाकी विफलताओं की श्रेणी में आए, विवरण ले जाने वाला एक `final` फ़ील्ड, और एक ओवरराइड किया हुआ `toString()` ताकि unhandled-exception रिपोर्ट पढ़ने योग्य रहे। वह ओवरराइड न हो तो Dart बस क्लास का नाम प्रिंट करता है और विवरण खो जाता है।

---

Dart दो परिवारों की वस्तुएँ फेंकता है, और वे एक-दूसरे के विपरीत अर्थ रखती हैं।

एक **`Exception`** ऐसी स्थिति बताता है जिसे प्रोग्राम नियंत्रित नहीं कर सकता: संख्या न रहा टेक्स्ट, वह फ़ाइल जो वहाँ थी ही नहीं, वह नेटवर्क जिसने कुछ जवाब नहीं दिया। `FormatException` उन्हीं में से एक है। ये अपेक्षित होते हैं, और उन्हें पकड़ना ही सामान्य प्रतिक्रिया है।

एक **`Error`** स्वयं कोड में गलती बताता है:

- `ArgumentError` — किसी फंक्शन को ऐसे मान के साथ बुलाया गया जिसे वह अपने दस्तावेज़ में अमान्य बताता है
- `StateError` — किसी वस्तु का उपयोग उस क्षण किया गया जब वह पूछी गई बात नहीं कर सकती थी
- `RangeError` — कोई इंडेक्स या मान अनुमत सीमा से बाहर था

एक `Error` पकड़ना बग को ठीक करने के बजाय उसे छिपा देता है। सही उत्तर है कोड बदलना ताकि वह फेंका ही न जाए: बुलाने से पहले आर्ग्युमेंट जाँचें, या ऐसा API उपयोग करें जो न फेंके। इसीलिए एक `on FormatException` क्लॉज़ अच्छी प्रथा है, जबकि एक `on ArgumentError` क्लॉज़ लगभग हमेशा नहीं होता।

---

कुछ लाइब्रेरियाँ ऐसा रूप भी देती हैं जो बिल्कुल भी नहीं फेंकता। `int.parse` के साथ-साथ Dart के पास **`int.tryParse`** भी है: वही रूपांतरण, पर जब टेक्स्ट संख्या न हो तो फेंकने के बजाय वह `null` लौटाता है।

```dart
print(int.parse('42'));     // 42
print(int.tryParse('42'));  // 42
print(int.tryParse('42x')); // null
```

परिणाम एक `int?` होता है, इसलिए `??` ऑपरेटर उसे सीधे एक डिफ़ॉल्ट मान में बदल देता है:

```dart
final port = int.tryParse(text) ?? 8080;
```

जब विफलता साधारण हो और आप केवल एक फ़ॉलबैक चाहते हों, तो यह एक `try` ब्लॉक से छोटा और स्पष्ट है। `int.parse` उन हालतों के लिए रखें जहाँ खराब टेक्स्ट सचमुच वह विफलता है जिसके बारे में ऊपर किसी को पता होना ही चाहिए।

---

`firstWhere` जाँच से मेल खाने वाला पहला तत्व लौटाता है। जब कुछ मेल न खाए तो लौटाने को कोई तत्व नहीं होता, इसलिए वह एक `StateError` फेंकता है:

```dart
final words = ['a', 'fg'];
print(words.firstWhere((w) => w.length > 3)); // Bad state: No element
```

`int.tryParse` की तरह, लाइब्रेरी एक रास्ता भी देती है। नामित पैरामीटर `orElse` एक फंक्शन लेता है जो वह मान बनाता है जो तब उपयोग हो जब कुछ मेल न खाए:

```dart
print(words.firstWhere((w) => w.length > 3, orElse: () => 'none')); // none
```

चुनाव वही है जो पहले था: `orElse` जब "कुछ मेल नहीं मिला" एक साधारण परिणाम हो, और बिना `orElse` वाला कॉल जब उसका मतलब हो कि डेटा खराब है और उसके बारे में किसी को पता होना चाहिए।

---

`throw` और `try` को एक ही फंक्शन में रहने की ज़रूरत नहीं। जो फंक्शन अपना काम नहीं कर सकता वह फेंकता है, और वह कॉलर पकड़ता है जो जानता है कि उसके बारे में क्या करना है:

```dart
int ageFromText(String text) {
  final age = int.tryParse(text);
  if (age == null) throw FormatException('not a number');
  return age;
}
```

`ageFromText` की कोई राय नहीं कि खराब उम्र से प्रोग्राम का अंत होना चाहिए, कोई संदेश दिखना चाहिए या उसे छोड़ दिया जाए — वह निर्णय कॉलर का है, और कॉलर ही वह जगह है जहाँ `try` ब्लॉक होना चाहिए। यही बँटवारा है जिसकी वजह से फेंकना `-1` लौटाने से ज़्यादा कीमती है: विफलता उसी एक जगह तक पहुँचती है जो उसका जवाब दे सकती है।

याद रखें कि `try` ब्लॉक पहली विफलता पर रुक जाता है, इसलिए विफल कॉल के बाद वाले कथन भी छोड़ दिए जाते हैं।

---

`try` ब्लॉक कहाँ बैठता है, यह तय करता है कि एक अकेली विफलता कितना काम बर्बाद कर देती है। लूप के चारों ओर होने पर पहला खराब तत्व पूरे बैच का अंत कर देता है; लूप के **अंदर** केवल वही तत्व खोता है और बाकी अब भी प्रोसेस होते हैं:

```dart
for (final text in texts) {
  try {
    total += int.parse(text);
  } on FormatException {
    continue;
  }
}
```

यही रोज़मर्रा का ढाँचा है किसी फ़ाइल को इंपोर्ट करने, सेटिंग्स की सूची पढ़ने या संदेशों की कतार संभालने के लिए: एक खराब पंक्ति से सही पंक्तियों को नहीं फेंकना चाहिए। नियम वही रहता है जो पहले था — `try` ब्लॉक को उस कथन के चारों ओर रखें जो विफल हो सकता है, और उससे बड़ा नहीं।

---

आख़िरी टुकड़ा है जानबूझकर एक `Error` फेंकना। जो फंक्शन बताता है कि वह क्या स्वीकार करता है, उसे बाकी सब कुछ ऊँची आवाज़ में ठुकरा देना चाहिए, और इसके लिए `ArgumentError` वही वस्तु है:

```dart
int setVolume(int level) {
  if (level < 0 || level > 100) {
    throw ArgumentError('level must be between 0 and 100');
  }
  return level;
}
```

संदेश `e.message` के रूप में मिलता है, और `toString()` उसके आगे `Invalid argument(s): ` प्रिंट करता है।

यह पहले वाले नियम के विपरीत नहीं है। एक `ArgumentError` फेंकना सही है, एक को पकड़ना नहीं: वह *कॉलर के* लेखक को बताता है कि कॉल स्वयं गलत है, और समाधान है कॉल से पहले की एक जाँच, उसके चारों ओर कोई हैंडलर नहीं।

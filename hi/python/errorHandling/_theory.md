**अपवाद (exception)** Python का यह बताने का तरीका है कि कोई स्टेटमेंट पूरा नहीं किया जा सकता। शून्य से भाग देना, `"abc"` को इंटीजर में बदलना या डिक्शनरी की गायब कुंजी पढ़ना — ये सभी एक अपवाद उत्पन्न करते हैं। जब उसे संभालने वाला कोई नहीं होता, तो प्रोग्राम वहीं रुक जाता है और एक **ट्रेसबैक (traceback)** प्रिंट करता है:
```python
print(10 / 0)
```
```
Traceback (most recent call last):
  File "main.py", line 1, in <module>
    print(10 / 0)
          ~~~^~~
ZeroDivisionError: division by zero
```
ट्रेसबैक चल रही लाइनों की सूची दिखाता है, और आखिरी लाइन **अपवाद का टाइप** (`ZeroDivisionError`) और उसका मैसेज (`division by zero`) बताती है। आखिरी लाइन को सबसे पहले पढ़ना चाहिए।

प्रोग्राम को चालू रखने के लिए, जोखिम भरे स्टेटमेंट को `try` ब्लॉक में रखें और उबरने का तरीका `except` ब्लॉक में लिखें:
```python
try:
    print(10 / 0)
except ZeroDivisionError:
    print("cannot divide by zero")
```
Python `try` ब्लॉक चलाता है; अगर बताया गया अपवाद उत्पन्न होता है तो वह सीधे मैच करने वाले `except` ब्लॉक पर कूद जाता है और प्रोग्राम का बाकी हिस्सा चलाता रहता है।

---

`try` ब्लॉक **पहले** उस स्टेटमेंट पर रुक जाता है जो अपवाद उत्पन्न करता है; उसके बाद की लाइनें छोड़ दी जाती हैं और कंट्रोल `except` ब्लॉक पर चला जाता है। `try` ब्लॉक में कुछ भी वापस नहीं किया जाता, इसलिए इसे जितना संभव हो उतना छोटा रखें:
```python
def half(n):
    try:
        return 10 / n
    except ZeroDivisionError:
        return "undefined"

print(half(2))  # 5.0
print(half(0))  # undefined
```
`except` के अंदर `return`, किसी और `return` की तरह ही काम करता है, जिससे `try`/`except` क्रैश होने के बजाय एक फॉलबैक मान लौटाने का सहज तरीका बन जाता है।

---

जिस अपवाद से कोई `except` ब्लॉक मैच नहीं होता, वह बाहर की ओर चलता रहता है: लाइन से बाहर, उसे चलाने वाले फंक्शन से बाहर, उसके कॉलर से बाहर, और इसी तरह आगे। अगर प्रोग्राम के सबसे ऊपर तक पहुँचने से पहले उसे कोई नहीं पकड़ता, तो Python ट्रेसबैक प्रिंट करता है और प्रोसेस नॉन-ज़ीरो एग्ज़िट स्टेटस के साथ खत्म होती है। फेल होने वाले स्टेटमेंट के बाद की लाइनें कभी नहीं चलतीं।

---

एक `except` क्लॉज़ केवल वही टाइप पकड़ता है जिसका नाम उसमें लिखा होता है, और उसकी सबक्लासेस। यही तो मकसद है: बाकी सब कुछ बाहर की ओर चलता रहता है, ताकि कोई अनजान बग निगला न जाए बल्कि ट्रेसबैक की तरह सामने आए।

`int(text)` **`ValueError`** उत्पन्न करता है जब टेक्स्ट कोई पूर्ण संख्या नहीं दर्शाता, इसलिए यूज़र इनपुट पढ़ते समय यही टाइप नाम से बताना चाहिए:
```python
def to_int(text):
    try:
        return int(text)
    except ValueError:
        return 0

print(to_int("12"))    # 12
print(to_int("oops"))  # 0
```
यहाँ `ValueError` का नाम लेना एक फैसला है, कोई औपचारिकता नहीं: `int(None)` `TypeError` उत्पन्न करता है, जिसे यह फंक्शन जान-बूझकर **नहीं** पकड़ता, क्योंकि `None` पास करना एक प्रोग्रामिंग की गलती है और उसे दिखना चाहिए।

---

जिस फेल होने की आपको उम्मीद है उसे कवर करने वाला सबसे सँकरा (narrowest) टाइप चुनना ही एरर हैंडलिंग को भरोसेमंद बनाता है। टेक्स्ट पढ़ने वाले फंक्शन को खराब टेक्स्ट (`ValueError`) से उबरना चाहिए, लेकिन गलत किस्म के आर्ग्युमेंट (`TypeError`) के साथ कॉल होने को छिपाना नहीं चाहिए — वह एरर कॉलर का होता है, इसलिए उसे आगे जाने दें।

---

एक `try` ब्लॉक के बाद **कई** `except` क्लॉज़ हो सकते हैं, हर एक अलग फेल होने को अलग रिकवरी से संभालता है। Python उत्पन्न हुए अपवाद की तुलना ऊपर से नीचे तक इनसे करता है और **पहला** मैच करने वाला चलाता है; बाकी छोड़ दिए जाते हैं:
```python
try:
    value = 100 / int(text)
except ValueError:
    print("not a number")
except ZeroDivisionError:
    print("cannot divide by zero")
```
चूँकि पहला मैच जीतता है, संबंधित टाइप्स के बीच क्रम मायने रखता है: एक सामान्य टाइप वाला क्लॉज़ अगर किसी ज़्यादा विशिष्ट टाइप वाले क्लॉज़ के ऊपर रखा हो तो हमेशा जीत जाएगा, और विशिष्ट क्लॉज़ कभी पहुँच ही नहीं पाएगा।

---

जब कई फेल होने **एक जैसी** रिकवरी के हकदार हों, तो उन्हें एक ही क्लॉज़ में टपल की तरह लिखना ब्लॉक दोहराने से छोटा होता है:
```python
try:
    value = int(text) / divisor
except (ValueError, ZeroDivisionError):
    value = 0
```
कोष्ठक ज़रूरी हैं: `except ValueError, ZeroDivisionError:` Python 3 में एक सिंटैक्स एरर है। टपल फिर भी टाइप्स की एक साफ़-साफ़ सूची है।

---

आगे कोई टाइप न होने वाला `except:` एक **bare except** है। यह हर चीज़ से मैच करता है, जिनमें वे अपवाद भी शामिल हैं जिनका उस क्रिया से कोई लेना-देना नहीं जिसे आप संभाल रहे थे, इसलिए नियम सीधा है: हमेशा उन्हीं टाइप्स का नाम लें जिनसे आप सच में उबर सकते हैं।

---

अपवाद एक ऑब्जेक्ट होता है, और `as` उसे एक नाम से बाँध देता है ताकि हैंडलर उसे देख सके:
```python
try:
    int("abc")
except ValueError as e:
    print(e)                   # invalid literal for int() with base 10: 'abc'
    print(type(e).__name__)    # ValueError
```
`str(e)` — जो `print(e)` और f-slot का उपयोग करता है — वही मैसेज देता है जिसके साथ अपवाद बना था, और `type(e).__name__` क्लास का नाम टेक्स्ट की तरह देता है। `as` से बँधा नाम केवल `except` ब्लॉक के अंदर मौजूद रहता है; ब्लॉक खत्म होने पर Python उसे डिलीट कर देता है।

---

एक `try` ब्लॉक के बाद एक `else` ब्लॉक हो सकता है, जो **केवल तब चलता है जब `try` ब्लॉक कोई अपवाद उत्पन्न किए बिना पूरा हुआ** हो:
```python
try:
    number = int(text)
except ValueError:
    print("not a number")
else:
    print(number * 2)
```
`print(number * 2)` को `try` ब्लॉक के अंदर रखने पर भी काम चल जाएगा, लेकिन तब प्रिंटिंग खुद से उत्पन्न हुआ `ValueError` कन्वर्ज़न के फेल होने समझा जा सकता है। `else` `try` ब्लॉक को सिर्फ़ उसी एक स्टेटमेंट तक सीमित रखता है जिसे संभाला जा रहा है, और सफलता पर होने वाली हर चीज़ को अपने पास रखता है।

---

`finally` ब्लॉक **हर हाल में** चलता है: बिना किसी गड़बड़ के पूरे हुए `try` ब्लॉक के बाद, किसी `except` ब्लॉक के बाद, यहाँ तक कि तब भी जब कोई पकड़ा न गया अपवाद बाहर की ओर जा रहा हो, और तब भी जब `try` या `except` ब्लॉक कोई `return` चला दे:
```python
def read(text):
    try:
        return int(text)
    except ValueError:
        return 0
    finally:
        print("done")
```
दोनों रास्तों पर मान के फंक्शन छोड़ने से पहले `done` प्रिंट होता है। यही गारंटी `finally` का मकसद है: फाइल बंद करना, लॉक छोड़ना, सेटिंग वापस लाना। पूरा ढाँचा `try` / `except` / `else` / `finally` है; `try` को कम से कम एक `except` या एक `finally` चाहिए, और `else` केवल `except` के साथ ही काम करता है।

---

आपका अपना कोड भी अपवाद उत्पन्न कर सकता है, `raise` स्टेटमेंट के बाद एक अपवाद ऑब्जेक्ट रखकर:
```python
def set_age(age):
    if age < 0:
        raise ValueError("age cannot be negative")
    return age
```
`raise` फंक्शन को तुरंत रोक देता है, बिल्कुल वैसे ही जैसे कोई बिल्ट-इन फेल होना रोकता है। इसकी जगह कोई एरर मान लौटाना — `-1`, `None`, `False` — कॉलर के लिए भूलना आसान है; अपवाद को गलती से नज़रअंदाज़ नहीं किया जा सकता।

वही टाइप चुनें जो समस्या को बताता है: `ValueError` जब आर्ग्युमेंट का टाइप सही हो पर मान नामुमकिन हो, `TypeError` जब टाइप ही गलत हो। अपवाद को दिया गया टेक्स्ट उसका मैसेज होता है।

---

कुछ बिल्ट-इन अपवाद रोज़मर्रा की ज़्यादातर फेल होने को कवर कर लेते हैं:

| अपवाद | कब उत्पन्न होता है | उदाहरण |
|---|---|---|
| `ValueError` | टाइप सही है पर मान नामुमकिन है | `int("abc")` |
| `TypeError` | टाइप ही गलत है | `"x" + 1` |
| `ZeroDivisionError` | भाग या मॉड्यूलो का भाजक शून्य है | `1 / 0` |
| `KeyError` | डिक्शनरी में ऐसी कुंजी नहीं है | `{"a": 1}["b"]` |
| `IndexError` | सीक्वेंस का इंडेक्स रेंज से बाहर है | `[1, 2][5]` |

नया टाइप गढ़ने के बजाय इनमें से किसी एक का उपयोग करने से आपके एरर Python जानने वाले किसी भी व्यक्ति के लिए पढ़ने योग्य रहते हैं।

---

कभी-कभी हैंडलर को किसी फेल होने पर प्रतिक्रिया देनी चाहिए पर उसकी ज़िम्मेदारी लिए बिना: उसे लॉग करना, गिनना, कुछ बंद करना — और फिर कॉलर पर छोड़ देना। `except` ब्लॉक के अंदर अकेला `raise` संभाले जा रहे अपवाद को **दोबारा उत्पन्न (re-raise)** करता है, उसका असली टाइप, मैसेज और ट्रेसबैक यथावत रखते हुए:
```python
try:
    value = int(text)
except ValueError:
    print("could not read the value")
    raise
```
इसकी जगह `raise ValueError(...)` लिखने से एक नया अपवाद अपने खुद के ट्रेसबैक के साथ बनेगा — यह वही फेल होना नहीं रह जाएगा जिसे आपने पकड़ा था, और यही पहचान एक अकेला `raise` सुरक्षित रखता है।

---

जब कोई बिल्ट-इन टाइप फिट न हो, तो `Exception` की सबक्लास बनाकर अपना खुद का परिभाषित करें। खाली बॉडी आम तौर पर काफ़ी होती है — नाम ही पाठक को मिलने वाला मैसेज है:
```python
class ConfigError(Exception):
    pass
```
यह किसी और अपवाद की तरह ही व्यवहार करता है: `raise ConfigError("bad port")`, और `except ConfigError:` उसे पकड़ लेता है।

किसी लो-लेवल फेल होने को अपने टाइप में बदलना आम बात है, और इस प्रक्रिया में असली एरर खोना नहीं चाहिए। `raise NewError(...) from original` दोनों को **जोड़ता (chain)** है: यह `original` को नए अपवाद के `__cause__` एट्रिब्यूट में सँजोता है, और ट्रेसबैक दोनों को *The above exception was the direct cause of the following exception* के नीचे दिखाता है:
```python
try:
    port = int(text)
except ValueError as e:
    raise ConfigError("bad port") from e
```
`from e` के बिना भी दोनों अप्रत्यक्ष रूप से जुड़े रहते हैं, पर `from` साफ़ शब्दों में कहता है कि पहले एरर ने दूसरा पैदा किया।

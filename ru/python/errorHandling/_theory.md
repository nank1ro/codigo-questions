**Исключение** (exception) — это способ Python сообщить, что инструкцию невозможно выполнить. Деление на ноль, преобразование `"abc"` в целое число или чтение отсутствующего ключа словаря — всё это вызывает исключение. Если его никто не обрабатывает, программа останавливается прямо на этом месте и печатает **трассировку** (traceback):
```python
print(10 / 0)
```
```
Traceback (most recent call last):
  File "main.py", line 1, in <module>
    print(10 / 0)
          ~~~^~~
ZeroDivisionError: division by zero
```
В трассировке перечислены строки, которые выполнялись, а последняя строка называет **тип исключения** (`ZeroDivisionError`) и его сообщение (`division by zero`). Именно с последней строки стоит начинать чтение.

Чтобы программа продолжила работу, поместите рискованную инструкцию в блок `try` и опишите восстановление в блоке `except`:
```python
try:
    print(10 / 0)
except ZeroDivisionError:
    print("cannot divide by zero")
```
Python выполняет блок `try`; если вызвано указанное исключение, он сразу переходит к соответствующему блоку `except` и продолжает выполнение остальной программы.

---

Блок `try` останавливается на **первой** инструкции, которая вызывает исключение; следующие за ней строки пропускаются, и управление переходит к блоку `except`. Ничего из сделанного в блоке `try` не отменяется, поэтому держите его как можно короче:
```python
def half(n):
    try:
        return 10 / n
    except ZeroDivisionError:
        return "undefined"

print(half(2))  # 5.0
print(half(0))  # undefined
```
`return` внутри `except` работает как любой другой `return`, поэтому `try`/`except` — естественный способ вернуть запасное значение вместо падения программы.

---

Исключение, которому не соответствует ни один блок `except`, продолжает распространяться наружу: из строки, из функции, которая его вызвала, из её вызывающей функции и так далее. Если ничего не перехватит его до вершины программы, Python печатает трассировку, и процесс завершается с ненулевым кодом выхода. Строки после неудавшейся инструкции никогда не выполняются.

---

Ветка `except` перехватывает только тот тип, который называет, и его подклассы. В этом и смысл: всё остальное продолжает распространяться наружу, поэтому неожиданная ошибка по-прежнему проявится как трассировка, а не будет проглочена.

`int(text)` вызывает **`ValueError`**, когда текст не описывает целое число, поэтому именно этот тип следует называть при чтении пользовательского ввода:
```python
def to_int(text):
    try:
        return int(text)
    except ValueError:
        return 0

print(to_int("12"))    # 12
print(to_int("oops"))  # 0
```
Указание `ValueError` здесь — это решение, а не формальность: `int(None)` вызывает `TypeError`, который эта функция сознательно **не** перехватывает, потому что передача `None` — программная ошибка, и её нужно увидеть.

---

Именно выбор самого узкого типа, покрывающего ожидаемый сбой, делает обработку ошибок надёжной. Функция, читающая текст, должна восстанавливаться после плохого текста (`ValueError`), но не должна скрывать вызов с аргументом неверного вида (`TypeError`) — эта ошибка принадлежит вызывающему, так что пусть она проходит дальше.

---

За одним блоком `try` могут следовать **несколько** веток `except`, каждая из которых обрабатывает свой сбой своим способом восстановления. Python сравнивает вызванное исключение с ними сверху вниз и выполняет **первую** подходящую; остальные пропускаются:
```python
try:
    value = 100 / int(text)
except ValueError:
    print("not a number")
except ZeroDivisionError:
    print("cannot divide by zero")
```
Поскольку побеждает первое совпадение, порядок важен, когда типы связаны: ветка для общего типа, поставленная над веткой для более конкретного, всегда побеждала бы, делая конкретную ветку недостижимой.

---

Когда несколько сбоев заслуживают **одинакового** восстановления, короче перечислить их кортежем в одной ветке, чем повторять блок:
```python
try:
    value = int(text) / divisor
except (ValueError, ZeroDivisionError):
    value = 0
```
Скобки обязательны: `except ValueError, ZeroDivisionError:` — синтаксическая ошибка в Python 3. Кортеж при этом остаётся явным списком типов.

---

`except:` без типа после себя — это **голый except**. Он соответствует всему, включая исключения, не имеющие никакого отношения к операции, которую вы защищали, поэтому правило простое: всегда называйте типы, от которых вы действительно можете восстановиться.

---

Исключение — это объект, и `as` привязывает его к имени, чтобы обработчик мог на него посмотреть:
```python
try:
    int("abc")
except ValueError as e:
    print(e)                   # invalid literal for int() with base 10: 'abc'
    print(type(e).__name__)    # ValueError
```
`str(e)` — его используют `print(e)` и f-слот — даёт сообщение, с которым исключение было создано, а `type(e).__name__` даёт имя класса в виде текста. Имя, привязанное через `as`, существует только внутри блока `except`; Python удаляет его, когда блок заканчивается.

---

За блоком `try` может следовать блок `else`, который выполняется, **только когда блок `try` завершился без исключения**:
```python
try:
    number = int(text)
except ValueError:
    print("not a number")
else:
    print(number * 2)
```
Поместить `print(number * 2)` внутрь блока `try` тоже сработало бы, но тогда `ValueError`, вызванный самим выводом, можно было бы принять за сбой преобразования. `else` удерживает блок `try` в рамках одной защищаемой инструкции и вмещает всё, что должно произойти при успехе.

---

Блок `finally` выполняется **при любом исходе**: после безошибочного блока `try`, после блока `except`, даже пока неперехваченное исключение распространяется наружу, и даже когда блок `try` или `except` выполняет `return`:
```python
def read(text):
    try:
        return int(text)
    except ValueError:
        return 0
    finally:
        print("done")
```
Оба пути выводят `done` до того, как значение покинет функцию. Именно ради такой гарантии существует `finally`: закрыть файл, освободить блокировку, вернуть настройку. Полная форма — `try` / `except` / `else` / `finally`; блоку `try` нужен хотя бы один `except` или `finally`, а `else` работает только вместе с `except`.

---

Ваш собственный код тоже может вызывать исключения — с помощью инструкции `raise`, за которой следует объект исключения:
```python
def set_age(age):
    if age < 0:
        raise ValueError("age cannot be negative")
    return age
```
`raise` немедленно останавливает функцию, точно так же, как это сделал бы встроенный сбой. Вернуть вместо этого значение-ошибку — `-1`, `None`, `False` — вызывающий легко может забыть проверить; исключение же невозможно проигнорировать случайно.

Выбирайте тип, описывающий проблему: `ValueError`, когда у аргумента правильный тип, но невозможное значение, и `TypeError`, когда неверен сам тип. Текст, переданный исключению, — это его сообщение.

---

Горстка встроенных исключений покрывает большинство повседневных сбоев:

| Exception | Raised when | Example |
|---|---|---|
| `ValueError` | тип правильный, но значение невозможно | `int("abc")` |
| `TypeError` | неверен сам тип | `"x" + 1` |
| `ZeroDivisionError` | у деления или остатка нулевой делитель | `1 / 0` |
| `KeyError` | в словаре нет такого ключа | `{"a": 1}["b"]` |
| `IndexError` | индекс последовательности вне диапазона | `[1, 2][5]` |

Обращение к одному из них вместо изобретения нового типа сохраняет ваши ошибки понятными любому, кто знает Python.

---

Иногда обработчик должен отреагировать на сбой, не беря за него ответственность: записать в журнал, посчитать, закрыть что-то — а дальше пусть с этим разбирается вызывающий. Одинокий `raise` внутри блока `except` **повторно вызывает** обрабатываемое исключение с исходными типом, сообщением и трассировкой:
```python
try:
    value = int(text)
except ValueError:
    print("could not read the value")
    raise
```
Написать вместо этого `raise ValueError(...)` значило бы создать новое исключение с собственной трассировкой — это была бы уже не та же ошибка, которую вы поймали, а именно эту идентичность и сохраняет одинокий `raise`.

---

Когда ни один встроенный тип не подходит, определите свой, унаследовав от `Exception`. Пустого тела обычно достаточно — имя и есть послание читателю:
```python
class ConfigError(Exception):
    pass
```
Он ведёт себя как любое другое исключение: `raise ConfigError("bad port")`, а `except ConfigError:` его перехватывает.

Превращать сбой низкого уровня в свой тип — обычное дело, и исходная ошибка не должна теряться в этом процессе. `raise NewError(...) from original` **связывает** их: он сохраняет `original` в атрибуте `__cause__` нового исключения, и трассировка показывает оба под заголовком *The above exception was the direct cause of the following exception*:
```python
try:
    port = int(text)
except ValueError as e:
    raise ConfigError("bad port") from e
```
Без `from e` они всё равно связаны неявно, но `from` прямо говорит, что первая ошибка стала причиной второй.

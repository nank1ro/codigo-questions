**Комментарий** — это заметка внутри исходного кода, предназначенная для тех, кто его читает. Компилятор полностью игнорирует комментарии, поэтому они никогда не меняют то, что делает программа.

Самый простой комментарий — это **однострочный комментарий**: он начинается с `//` и продолжается до конца строки.
```kotlin
// Приветствует пользователя
println("Hello")
```
Используйте комментарии, чтобы объяснить, для чего нужен фрагмент кода или почему он написан именно так.

---

Комментарию не обязательно занимать отдельную строку: он может следовать за кодом в той же строке. Это **комментарий в конце строки**, и это удачное место для короткой заметки о конкретной инструкции:
```kotlin
val retries = 3 // сдаться после трёх попыток
```
Всё от `//` до конца строки игнорируется, а код перед ним выполняется как обычно.

---

Поскольку компилятор полностью удаляет комментарии, добавление или удаление комментария никогда не меняет поведение программы. Выполняется только тот код, который **не** закомментирован.

Поэтому `//` — это быстрый способ выключить строку кода, не удаляя её. Это называется **закомментированием**:
```kotlin
var total = 10
// total = total + 5
println(total) // выводит 10
```
Вторая строка теперь является комментарием, поэтому `total` остаётся равным `10`. Удаление `//` возвращает строку к жизни.

Закомментирование удобно во время экспериментов, но не забывайте убирать за собой: код, который долго остаётся закомментированным, только сбивает с толку того, кто будет читать его после вас.

---

Когда комментарий занимает несколько строк, Kotlin предлагает **многострочный комментарий** (его также называют блочным комментарием): он начинается с `/*` и заканчивается `*/`, и всё, что находится между ними, игнорируется, включая переводы строк.
```kotlin
/*
  Prints the welcome banner.
  Called once when the app starts.
*/
println("Welcome!")
```
Блочный комментарий может быть и коротким, умещаясь на одной строке: `/* like this */`.

---

В отличие от `//`, который останавливается в конце строки, комментарий `/*` останавливается только на `*/`. Если вы забудете его закрыть, компилятор сочтёт весь следующий код частью комментария и сообщит об ошибке:
```kotlin
val width = 10 /* в сантиметрах
println(width) // всё ещё внутри комментария: ошибка, комментарий так и не закрыт
```
И `//`, и `/* */` могут использоваться как комментарии в конце строки, но с `/*` всегда проверяйте, что `*/` на месте.

---

В Java блочный комментарий не может содержать другой блочный комментарий, но в Kotlin они **могут быть вложенными**: каждая `/*` должна быть закрыта своей `*/`, и комментарий заканчивается только тогда, когда закрыт самый внешний.
```kotlin
/* outer /* inner */ still a comment */
println("done")
```
Здесь `still a comment */` является частью внешнего комментария, поэтому выводится только `done`. Именно это позволяет закомментировать целый блок кода, даже если этот блок уже содержит комментарий `/* */`.

---

Чтобы закомментировать несколько строк сразу, оберните их одним блочным комментарием вместо того, чтобы добавлять `//` в каждую строку:
```kotlin
var total = 100
/*
total = total - 30
total = total - 20
*/
println(total) // выводит 100
```
Благодаря вложенности это работает даже тогда, когда одна из этих строк уже содержит комментарий `/* */`.

---

Распространённое применение блочных комментариев — **комментарий-заголовок**: небольшой блок, размещённый непосредственно над функцией, который говорит, что она делает и что означают её параметры.
```kotlin
/*
Returns the number of seconds in the given minutes.
minutes is a whole number, never negative.
*/
fun toSeconds(minutes: Int): Int {
    return minutes * 60
}
```
Тот, кто вызывает `toSeconds`, может прочитать заголовок вместо тела функции. Держите заголовок рядом с функцией, чтобы они обновлялись вместе.

---

В Kotlin есть третий вид комментария — **документирующий комментарий**, написанный в формате под названием **KDoc**: он начинается с `/**` (слэш и две звёздочки) и заканчивается `*/`, и размещается непосредственно над функцией, классом или свойством.
```kotlin
/**
 * Returns the greeting for [name].
 */
fun greet(name: String): String {
    return "Hi, $name!"
}
```
Для компилятора это просто комментарий, но такие инструменты, как IntelliJ IDEA, читают его и показывают как справку для `greet`. Звёздочка `*` в начале внутренних строк — это лишь соглашение, которое сохраняет выравнивание блока. Внутри KDoc можно использовать Markdown, а квадратные скобки вроде `[name]` превращаются в ссылки на этот параметр.

---

Первая строка документирующего комментария — это **краткое описание**: короткое предложение, которое говорит, что делает функция. Пишите его в третьем лице, как будто описывая функцию: "Returns...", "Adds...", "Checks...".
```kotlin
/**
 * Returns `true` when [n] is divisible by two.
 */
fun isEven(n: Int): Boolean {
    return n % 2 == 0
}
```
Комментарий должен находиться прямо над объявлением, без других инструкций между ними, иначе инструменты не привяжут его к функции.

---

После краткого описания документирующий комментарий может описывать параметры и возвращаемое значение с помощью **тегов KDoc**, которые всегда начинаются с `@`:
```kotlin
/**
 * Returns the number of seconds in the given minutes.
 * @param minutes a whole number of minutes, never negative
 * @return [minutes] multiplied by sixty
 */
fun toSeconds(minutes: Int): Int {
    return minutes * 60
}
```
За `@param` следует имя параметра, а затем его описание; для каждого параметра — свой `@param`. `@return` описывает значение, которое возвращает функция. Порядок всегда одинаковый: сначала краткое описание, затем теги `@param`, затем `@return`.

---

Функция с более чем одним параметром получает по тегу `@param` на каждый из них, записанные в том же порядке, что и параметры:
```kotlin
/**
 * Returns the area of a rectangle.
 * @param width the horizontal side, in centimetres
 * @param height the vertical side, in centimetres
 * @return the product of [width] and [height]
 */
fun area(width: Int, height: Int): Int {
    return width * height
}
```
Тег — это по-прежнему всего лишь комментарий: если вы переименуете параметр и забудете про тег, ничего не сломается, но документация начнёт лгать. Обновляйте KDoc вместе с сигнатурой.

---

Компилятор ищет комментарии только в коде, но никогда — внутри **строкового литерала**. Между двойными кавычками `//` и `/* */` являются обычными символами:
```kotlin
println("50 // 2") // prints 50 // 2
```
Первый `//` — часть текста, второй начинает настоящий комментарий. Чаще всего это удивляет людей на веб-адресах, которые содержат `//` сразу после протокола.

---

Некоторые комментарии следуют соглашениям, которые понимают редакторы. Самые распространённые **маркеры**:
- `// TODO: ...` помечает то, что ещё нужно написать
- `// FIXME: ...` помечает код, который заведомо неверен и должен быть исправлен

```kotlin
val limit = 10
// TODO: считать лимит из настроек
```
Для компилятора это обычные комментарии; IntelliJ IDEA собирает их в отдельном окне инструментов, чтобы незавершённую работу было легко найти. `TODO` обычно стоит рядом с заглушкой, которая позволяет коду компилироваться, пока не будет написана настоящая реализация. Завершив работу, замените заглушку и удалите маркер одним изменением, чтобы комментарий никогда не лгал о состоянии кода.

---

`FIXME` отличается от `TODO`: код уже существует, но известно, что он неверен. Хороший `FIXME` говорит, в чём заключается ошибка, и, когда это возможно, приводит пример, который её демонстрирует, чтобы следующий человек мог быстро её исправить. Как и в случае с `TODO`, удалите маркер, как только ошибка исправлена, но сохраните документирующий комментарий — он по-прежнему верен.

---

Хороший комментарий объясняет, **почему** код что-то делает, а не **что** он делает. Код и так показывает, что происходит; повторение этого словами добавляет шум и устаревает, как только код меняется:
```kotlin
// установить timeout в 30
val timeout = 30
```
Причина, стоящая за числом, — это то, что читатель не сможет угадать:
```kotlin
// сервер разрывает простаивающие соединения через 35 секунд, так что остановись раньше
val timeout = 30
```
Если комментарий лишь повторяет строку под ним, удалите его или замените причиной. Лучшие комментарии — те, которые говорят то, чего не может сказать код.

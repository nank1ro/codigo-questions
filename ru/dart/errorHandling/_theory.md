Некоторые инструкции невыполнимы: чтение текста, который не является числом, обращение к элементу за концом списка, запрос первого элемента пустого списка. Когда это происходит, Dart **выбрасывает** объект, описывающий сбой.

Вы можете выбросить такой объект сами с помощью ключевого слова `throw`. `Exception('message')` создаёт готовый объект с кратким пояснением:

```dart
throw Exception('no fuel');
```

Оператор `throw` — это не `return`. Он прерывает инструкцию, функцию и всех вызывающих выше по цепочке, отправляясь на поиски того, кто его обработает. Если таких нет, программа останавливается и печатает сообщение о сбое:

```
Unhandled exception:
Exception: no fuel
```

Всё после выброса пропускается, поэтому строки, которые должны были выполниться, никогда не выполнятся. Именно об этом эта тема: решать, где обрабатывается сбой, вместо того чтобы позволить ему завершить программу.

---

Чтобы программа продолжила работу, оберните рискованную инструкцию в блок `try`, а восстановление опишите в блоке `catch`:

```dart
try {
  print(int.parse('twelve'));
} catch (e) {
  print('that is not a number');
}
```

`int.parse` выбрасывает исключение, когда текст не описывает целое число. Dart покидает блок `try` на первой же инструкции, выбросившей исключение, пропускает остаток блока, выполняет блок `catch`, а затем продолжает код, идущий дальше. Переменная в круглых скобках — здесь `e` — это и есть выброшенный объект.

Ничто внутри блока `try` не откатывается, поэтому делайте его не длиннее сбоя, которого ожидаете.

---

Голый `catch` перехватывает всё, а заодно скрывает и те сбои, которые вы не планировали. Чтобы обработать ровно один вид, укажите его тип в предложении `on`:

```dart
try {
  return int.parse(text);
} on FormatException catch (e) {
  return -1;
}
```

`int.parse` выбрасывает **`FormatException`**, когда текст не является целым числом, поэтому именно этот тип нужно указывать при чтении ввода. Предложение `on` соответствует этому типу и его подтипам — и ничему больше: любой другой сбой продолжает распространяться наружу и всё равно проявится, вместо того чтобы быть поглощённым восстановлением, которое для него не предназначалось.

---

За одним блоком `try` могут следовать **несколько** предложений, каждое из которых восстанавливается после своего сбоя. Dart сравнивает выброшенный объект с ними сверху вниз и выполняет **первое** совпавшее:

```dart
try {
  return names[int.parse(text)];
} on FormatException {
  return 'not a number';
} on RangeError {
  return 'out of range';
} catch (e) {
  return 'unknown problem';
}
```

Чтение списка по индексу, которого не существует, выбрасывает **`RangeError`**, поэтому два сбоя одной и той же строки получают разные ответы.

Поскольку побеждает первое совпадение, порядок важен: предложение для общего типа, размещённое выше более специфичного, всегда победит, оставив специфичное предложение недостижимым. Пишите специфичные предложения первыми, а голый `catch` — последним, если нужна страховка.

Предложение `on RangeError` выше приведено лишь для того, чтобы показать, как упорядочены несколько предложений. `RangeError` сигнализирует об ошибке в коде, а не о состоянии, которое программа не могла контролировать, и в одном из следующих упражнений объясняется, почему такой сбой нужно предотвращать, а не перехватывать.

---

Часто восстановлению вообще не нужен выброшенный объект: тип уже говорит сам за себя. В этом случае уберите часть `catch` и оставьте только предложение `on`:

```dart
try {
  return int.parse(text);
} on FormatException {
  return 0;
}
```

Две формы различаются только тем, получаете ли вы переменную:

- `on FormatException catch (e)` — соответствует этому типу и даёт вам объект как `e`
- `on FormatException` — соответствует этому типу, без переменной
- `catch (e)` — соответствует всему и даёт вам объект

Опуская неиспользуемую переменную, вы делаете обработчик честным насчёт того, что он действительно использует.

---

За обработчиками может следовать третий блок. `finally` выполняется **в любом случае**: после нормального завершения блока `try`, после восстановившего обработчика, а также когда ничего не совпало и сбой всё ещё распространяется наружу.

```dart
try {
  return 'parsed ${int.parse(text)}';
} on FormatException {
  return 'failed';
} finally {
  print('done');
}
```

Он выполняется даже раньше, чем `return` вернёт значение, именно поэтому сообщение выше печатается до того, как вызывающий увидит результат. Это делает `finally` местом для работы, которая должна произойти в любом случае, например закрытия того, что вы открыли.

---

Ваш собственный код выбрасывает исключения так же, как библиотека. `Exception('message')` создаёт простое исключение с кратким пояснением, а `throw` отправляет его в путь:

```dart
if (amount > balance) {
  throw Exception('insufficient funds');
}
```

Сообщение не теряется: `toString()` складывает вместе слово `Exception`, двоеточие и сообщение — именно это печатает отчёт о необработанном исключении.

```dart
print(Exception('insufficient funds')); // Exception: insufficient funds
```

Выбрасывание лучше, чем возврат выдуманного значения вроде `-1`: вызывающий код не может забыть его проверить, а причина путешествует вместе с исключением.

---

Иногда обработчик — не то место, где стоит восстанавливаться: вы хотите лишь *заметить* сбой и позволить ему дойти до вызывающего кода, который действительно может с ним разобраться. Ключевое слово `rethrow` делает именно это — внутри блока `catch` или `on ... catch`:

```dart
try {
  return int.parse(text);
} on FormatException {
  log.add('bad input: $text');
  rethrow;
}
```

`rethrow` отправляет дальше **тот же** объект, поэтому вызывающий код видит исходный сбой. Запись `throw e` вместо него тоже сработала бы, но она начинает путь заново и теряет место, где сбой произошёл впервые.

Блок `finally` в той же инструкции всё равно выполняется, даже когда исключение уходит наружу.

---

Предложение `catch` принимает **второй** параметр:

```dart
try {
  return int.parse(text);
} on FormatException catch (e, s) {
  log.add('$e');
  log.add('$s');
  rethrow;
}
```

Первый — это выброшенный объект, второй — `StackTrace`: цепочка вызовов, выполнявшихся в момент выброса. Он отвечает на вопрос, *откуда* пришёл сбой, — на него одно лишь сообщение редко позволяет ответить.

Трассировка стека перечисляет имена файлов, номера строк и кадры, и она меняется в зависимости от сборки и пути вызова. Печатайте её, прикладывайте к отчёту, передавайте дальше — но никогда не сравнивайте её с фиксированным текстом и никогда не стройте поведение программы на её содержимом. Запрашивайте её, только когда собираетесь записать её в журнал.

---

`Exception` — это интерфейс, поэтому вашим классом тоже может стать исключение. Собственное исключение даёт сбою имя, которое предложение `on` может выбрать, и поля, которые обработчик может прочитать:

```dart
class EmptyCartException implements Exception {
  final String message;

  EmptyCartException(this.message);

  @override
  String toString() => 'EmptyCartException: $message';
}

throw EmptyCartException('nothing to pay for');
```

Три части стоит сохранить: `implements Exception`, чтобы класс принадлежал к остальным сбоям, поле `final` с подробностью и переопределённый `toString()`, чтобы отчёт о необработанном исключении был читаемым. Без этого переопределения Dart печатает только имя класса, и подробность теряется.

---

Dart выбрасывает объекты двух семейств, и они означают противоположные вещи.

**`Exception`** описывает состояние, которое программа не могла контролировать: текст, не являющийся числом, отсутствующий файл, сеть, не ответившая ничего. `FormatException` — один из них. Такие ситуации ожидаемы, и перехватывать их — нормальная реакция.

**`Error`** описывает ошибку в самом коде:

- `ArgumentError` — функция была вызвана со значением, которое она документирует как недопустимое
- `StateError` — объект был использован в момент, когда он не может сделать то, о чём просят
- `RangeError` — индекс или значение были вне допустимого диапазона

Перехват `Error` скрывает баг вместо того, чтобы исправить его. Правильный ответ — изменить код так, чтобы он перестал выбрасываться: проверить аргумент до вызова или использовать API, которое не выбрасывает. Именно поэтому предложение `on FormatException` — хорошая практика, а предложение `on ArgumentError` — почти всегда нет.

---

Некоторые библиотеки предлагают версию, которая вообще не выбрасывает. Рядом с `int.parse` в Dart есть **`int.tryParse`**: то же преобразование, но оно возвращает `null` вместо выброса исключения, когда текст не является числом.

```dart
print(int.parse('42'));     // 42
print(int.tryParse('42'));  // 42
print(int.tryParse('42x')); // null
```

Результат имеет тип `int?`, поэтому оператор `??` превращает его прямо в значение по умолчанию:

```dart
final port = int.tryParse(text) ?? 8080;
```

Когда сбой обычен и вам нужно только запасное значение, это короче и понятнее, чем блок `try`. Оставьте `int.parse` для случаев, когда плохой текст — действительно сбой, о котором кто-то выше должен узнать.

---

`firstWhere` возвращает первый элемент, соответствующий проверке. Когда ничего не соответствует, возвращать нечего, и он выбрасывает `StateError`:

```dart
final words = ['a', 'fg'];
print(words.firstWhere((w) => w.length > 3)); // Bad state: No element
```

Как и `int.tryParse`, библиотека предлагает выход. Именованный параметр `orElse` принимает функцию, которая создаёт значение для случая, когда ничего не совпало:

```dart
print(words.firstWhere((w) => w.length > 3, orElse: () => 'none')); // none
```

Выбор тот же, что и раньше: `orElse`, когда «ничего не совпало» — обычный исход, и вызов без него, когда это означало бы, что данные сломаны и кто-то должен об этом узнать.

---

`throw` и `try` не обязаны жить в одной функции. Функция, которая не может выполнить свою работу, выбрасывает исключение, а вызывающий код, знающий, что с ним делать, перехватывает:

```dart
int ageFromText(String text) {
  final age = int.tryParse(text);
  if (age == null) throw FormatException('not a number');
  return age;
}
```

`ageFromText` не решает, должен ли плохой возраст завершать программу, показывать сообщение или пропускаться — это решение вызывающего кода, и именно у него место блока `try`. Такое разделение — причина, по которой выбрасывание ценнее возврата `-1`: сбой доходит до того единственного места, которое может на него ответить.

Помните, что блок `try` останавливается на первом сбое, поэтому инструкции после неудавшегося вызова тоже пропускаются.

---

Расположение блока `try` определяет, сколько работы уничтожает один сбой. Вокруг цикла первый плохой элемент завершает всю партию; **внутри** цикла теряется только этот элемент, а остальные всё ещё обрабатываются:

```dart
for (final text in texts) {
  try {
    total += int.parse(text);
  } on FormatException {
    continue;
  }
}
```

Это повседневная форма для импорта файла, чтения списка настроек или обработки очереди сообщений: одна повреждённая строка не должна выбрасывать хорошие. Правило остаётся прежним — держите блок `try` вокруг инструкции, которая может дать сбой, и не больше.

---

Последний элемент — выброс `Error` намеренно. Функция, документирующая, что она принимает, должна громко отказывать всему остальному, и `ArgumentError` — объект для этого:

```dart
int setVolume(int level) {
  if (level < 0 || level > 100) {
    throw ArgumentError('level must be between 0 and 100');
  }
  return level;
}
```

Сообщение доступно как `e.message`, а `toString()` печатает `Invalid argument(s): ` с ним.

Это не противоречит правилу из прошлого упражнения. Выбросить `ArgumentError` — правильно, перехватить — нет: он сообщает автору *вызывающего кода*, что сам вызов неверен, и исправление — это проверка до вызова, а не обработчик вокруг него.

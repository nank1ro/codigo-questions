**Протокол** описывает, что должен иметь тип, не уточняя, как. Это список требований — свойств и методов, — который любой принимающий его тип обещает реализовать.

Протокол объявляется ключевым словом `protocol`. Требование к свойству записывается с указанием его типа, за которым следует блок, определяющий, как к нему можно обращаться: `{ get }` означает, что тип как минимум должен позволять его читать.
```swift
protocol Named {
    var name: String { get }
}
```
Тип **соответствует** протоколу, записывая его имя после двоеточия и предоставляя всё, что требует протокол:
```swift
struct Cat: Named {
    var name: String
}

let cat = Cat(name: "Luna")
print(cat.name) // Luna
```
Протокол сам не хранит данных: это контракт. Каждый тип, удовлетворяющий ему, может одинаково обрабатываться остальным вашим кодом.

---

Протокол может также требовать **методы**. Вы записываете сигнатуру — имя, параметры и тип возвращаемого значения — и на этом останавливаетесь, без тела:
```swift
protocol Greeter {
    func greet() -> String
}
```
Соответствующий тип должен объявить метод с точно такой сигнатурой и предоставить тело:
```swift
struct Robot: Greeter {
    func greet() -> String {
        return "BEEP"
    }
}

print(Robot().greet()) // BEEP
```
Если что-то отличается — имя, тип параметра, тип возвращаемого значения, — тип не соответствует протоколу, и компилятор сообщит, какого требования не хватает.

---

Требование к свойству всегда указывает, как это свойство можно использовать. `{ get }` требует лишь, чтобы значение можно было читать; `{ get set }` требует, чтобы его можно было читать **и** присваивать:
```swift
protocol Account {
    var owner: String { get }
    var balance: Int { get set }
}
```
Соответствующий тип всегда может дать больше, чем требует контракт: хранимое свойство `var` прекрасно удовлетворяет `{ get }`. Но он никогда не может дать меньше — константа `let` или вычисляемое свойство только для чтения не могут удовлетворить `{ get set }`.

---

Протоколами не ограничиваются структуры. **Класс** соответствует точно так же, указывая протокол после двоеточия:
```swift
protocol Openable {
    func open() -> String
}

class Door: Openable {
    func open() -> String {
        return "creak"
    }
}
```
Если класс также наследует другой класс, суперкласс идёт первым в списке, а протоколы следуют за ним. Тип может принимать несколько протоколов одновременно, разделяя их запятыми.

---

**Перечисление** тоже может соответствовать. У него нет хранимых свойств, поэтому требование к свойству обычно выполняется вычисляемым свойством, которое выполняет `switch` по вариантам:
```swift
protocol Priced {
    var price: Int { get }
}

enum Ticket: Priced {
    case child, adult

    var price: Int {
        switch self {
        case .child: return 5
        case .adult: return 12
        }
    }
}

print(Ticket.adult.price) // 12
```
Структуры, классы и перечисления: все три принимают протоколы одинаково, и код, написанный против протокола, работает со всеми ними.

---

Протокол обычно собирает более одного требования, и соответствующий тип должен выполнить каждое из них:
```swift
protocol Vehicle {
    var wheels: Int { get }
    func move() -> String
}

struct Bike: Vehicle {
    var wheels = 2

    func move() -> String {
        return "pedalling"
    }
}
```
Порядок требований внутри фигурных скобок не важен, как и порядок, в котором соответствующий тип их предоставляет: компилятор проверяет лишь, что ничего не пропущено.

---

Структура — это тип значения, поэтому метод, изменяющий одно из её хранимых свойств, должен быть помечен как `mutating`. Когда такой метод является требованием протокола, протокол тоже должен это указать:
```swift
protocol Togglable {
    mutating func toggle()
}

struct Light: Togglable {
    var isOn = false

    mutating func toggle() {
        isOn = !isOn
    }
}

var lamp = Light()
lamp.toggle()
print(lamp.isOn) // true
```
Без `mutating` в протоколе структура никогда не смогла бы удовлетворить требование. Классы — ссылочные типы и никогда не нуждаются в этом ключевом слове: класс выполняет `mutating`-требование обычным методом. Вызов мутирующего метода требует `var` — на `let` это ошибка компиляции.

---

Соответствие не обязательно объявлять рядом с типом. **Расширение** может добавить его позже, оставляя собственное объявление типа сосредоточенным на его данных:
```swift
protocol Resettable {
    mutating func reset()
}

struct Timer {
    var seconds = 0
}

extension Timer: Resettable {
    mutating func reset() {
        seconds = 0
    }
}
```
Это работает и для типов, которые вы не писали: можно сделать тип стандартной библиотеки соответствующим одному из ваших протоколов, не трогая его исходный код.

---

Расширение **протокола** — другой инструмент: оно добавляет члены каждому соответствующему типу, как существующему, так и будущему. Так вы даёте требованию **реализацию по умолчанию**:
```swift
protocol Greeter {
    var name: String { get }
    func greet() -> String
}

extension Greeter {
    func greet() -> String {
        return "Hi, \(name)"
    }
}

struct Person: Greeter {
    var name: String
}

print(Person(name: "Ada").greet()) // Hi, Ada
```
`Person` никогда не пишет `greet()` и всё же соответствует. Внутри расширения протокола можно использовать любое требование протокола — здесь `name`, — потому что любой соответствующий тип гарантированно его имеет.

---

Расширение протокола может также добавлять члены, которые протокол никогда не перечислял как требования. Это дополнительные удобства, доступные каждому соответствующему типу:
```swift
protocol Sized {
    var count: Int { get }
}

extension Sized {
    var isEmpty: Bool {
        return count == 0
    }
}
```
`isEmpty` — не требование, поэтому соответствующий тип не обязан его предоставлять — он просто получает его.

---

Протокол может строиться на другом. Запись имени протокола после двоеточия заставляет новый протокол **наследовать** каждое требование старого:
```swift
protocol Named {
    var name: String { get }
}

protocol Aged: Named {
    var age: Int { get }
}
```
Тип, соответствующий `Aged`, должен предоставить `age` *и* `name`, и он считается типом `Named` везде. Протокол может наследовать от нескольких протоколов одновременно, разделяя их запятыми.

---

Реализация по умолчанию — это запасной вариант, а не правило. Если соответствующий тип предоставляет собственную версию требования, выполняется именно его версия:
```swift
protocol Priced {
    var price: Int { get }
}

extension Priced {
    var price: Int { return 0 }
}

struct Ticket: Priced {
    var price = 12
}

print(Ticket().price) // 12, not 0
```
Реализация по умолчанию лишь заполняет пробелы, которые тип оставляет открытыми.

---

Стандартная библиотека построена из протоколов, и ваши собственные типы могут их принимать.

`Equatable` даёт типу оператор `==`. Для структуры, все хранимые свойства которой `Equatable`, достаточно объявить соответствие — Swift напишет `==` за вас:
```swift
struct Point: Equatable {
    var x: Int
    var y: Int
}

print(Point(x: 1, y: 2) == Point(x: 1, y: 2)) // true
```
`Comparable` наследует от `Equatable` и добавляет упорядочивание. Вы реализуете один оператор, `<`, записанный как `static func`, принимающий оба значения, и бесплатно получаете `>`, `<=`, `>=`, а также `sorted()`, `min()` и `max()` на коллекциях:
```swift
struct Version: Comparable {
    var number: Int

    static func < (lhs: Version, rhs: Version) -> Bool {
        return lhs.number < rhs.number
    }
}
```

---

`CustomStringConvertible` решает, что `print` показывает для вашего типа. Его единственное требование — свойство `description`:
```swift
struct Coin: CustomStringConvertible {
    var value: Int

    var description: String {
        return "\(value)c"
    }
}

print(Coin(value: 25)) // 25c
```
Без соответствия печать структуры возвращается к стандартному дампу вроде `Coin(value: 25)`, и одно лишь свойство `description` ничего не меняет — `print` ищет протокол. Строковая интерполяция тоже использует `description`.

---

Имя протокола само по себе — не тип, а ограничение, поэтому Swift просит вас указать, что из двух вы имеете в виду.

`some Shape` означает *один конкретный соответствующий тип*, фиксированный во время компиляции. Вызывающий код никогда не узнаёт, какой именно, но он всегда один и тот же:
```swift
func unitSquare() -> some Shape {
    return Square(side: 1)
}
```
`any Shape` означает *коробку, которая может хранить любой соответствующий тип*, и два значения такого типа могут хранить разные типы. Это нужно всякий раз, когда конкретный тип может меняться, например внутри смешанного массива:
```swift
let shapes: [any Shape] = [Square(side: 2), Rect(width: 2, height: 3)]
```
Оба позволяют вызывать требования протокола. Предпочитайте `some`, когда достаточно одного типа, потому что это ничего не стоит во время выполнения; обращайтесь к `any`, когда вам действительно нужно смешивать типы.

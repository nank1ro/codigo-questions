В Swift ошибка — это **значение**, а не аварийное падение. Любой тип может выступать в этой роли, приняв протокол `Error`, а перечисление — обычный выбор, ведь его варианты точно называют то, что может пойти не так:
```swift
enum LoginError: Error {
    case wrongPassword
}
```
Функция, которая может завершиться неудачей, помечается `throws` и сообщает о сбое с помощью `throw`:
```swift
func login(_ password: String) throws {
    if password != "swift" {
        throw LoginError.wrongPassword
    }
    print("welcome")
}
```
Вызов такой функции требует `try`, и он должен находиться внутри блока `do`, за которым следует блок `catch`, описывающий, что делать при сбое:
```swift
do {
    try login("hunter2")
} catch {
    print("login failed")
}
// login failed
```
Когда выполняется `throw`, остаток блока `do` пропускается и управление перехватывает `catch`. Ничего не падает: программа продолжает работу после `catch`.

---

Функция с `throws` всё равно может возвращать значение. Ключевое слово `throws` ставится между списком параметров и стрелкой возвращаемого значения:
```swift
func square(_ n: Int) throws -> Int {
    if n < 0 {
        throw SquareError.negative
    }
    return n * n
}
```
Прочитаем это вслух: *square принимает `Int`, может выбросить ошибку и возвращает `Int`*.

В месте вызова значение существует, только если ничего не было выброшено, поэтому присваивание находится внутри блока `do`:
```swift
do {
    let result = try square(4)
    print(result) // 16
} catch {
    print("failed")
}
```
`try` — не необязательное украшение: без него компилятор отклоняет вызов, поэтому читающий всегда видит, какие строки могут завершиться неудачей.

---

Голый `catch` обрабатывает любую ошибку одинаково. Чаще всего нужно отреагировать на один конкретный сбой, поэтому `catch` может нести **шаблон**: вариант, который он готов обработать.
```swift
do {
    try check("")
} catch ValidationError.empty {
    print("the text is empty")
} catch {
    print("something else")
}
```
Swift перебирает ветви `catch` сверху вниз и выполняет первую, чей шаблон совпал.

Последний `catch` намеренно оставлен без шаблона. `catch` с шаблоном покрывает только названный в нём вариант, а Swift требует, чтобы каждая ошибка была где-то обработана, поэтому блоку `do` с перечислением шаблонов нужен завершающий `catch` без шаблона, который подберёт всё остальное.

---

Порядок имеет значение. Swift сравнивает выброшенное значение с каждым шаблоном `catch` в том порядке, в каком они записаны, и останавливается на первом совпадении, поэтому `catch` без шаблона, стоящий первым, поглотил бы всё, что ниже него. Держите конкретные варианты сверху, а общий `catch` — снизу.

Ошибка, не совпавшая ни с одним из шаблонов, не игнорируется: она попадает в завершающий `catch` без шаблона.

---

Вариант ошибки может нести данные. Задайте варианту **связанные значения**, и `throw` заполнит их, так что обработчик узнает не только *что* завершилось неудачей, но и *насколько*:
```swift
enum ValidationError: Error {
    case tooShort(minimum: Int)
}

throw ValidationError.tooShort(minimum: 8)
```
Соответствующий `catch` привязывает эти значения с помощью `let`:
```swift
} catch ValidationError.tooShort(let minimum) {
    print("needs at least \(minimum) characters")
}
```
Имя после `let` выбираете вы; это новая константа, доступная только внутри этого блока `catch`. Так ошибка несёт полезное сообщение, и вам не приходится вставлять числа в строки там, где произошёл сбой.

---

Одно перечисление обычно собирает все способы, которыми может завершиться неудачей одна задача, — по варианту на каждую причину:
```swift
enum FormError: Error {
    case empty
    case tooLong
}
```
Писать по одному `catch` на каждый вариант утомительно. Вместо этого перехватите весь тип сразу и пройдитесь по значению с помощью `switch`:
```swift
} catch let error as FormError {
    switch error {
    case .empty: print("empty")
    case .tooLong: print("too long")
    }
} catch {
    print("unknown")
}
```
`catch let error as FormError` означает *перехвати всё, что является `FormError`, и назови это `error`*. Внутри блока `error` имеет тип перечисления, поэтому `switch` видит варианты и проверяет, что покрыты все они. Завершающий `catch` без шаблона по-прежнему обязателен, ведь в этот блок `do` может попасть ошибка и другого типа.

---

Валидатор читается лучше всего, когда отказы идут первыми, а настоящая работа остаётся внизу без отступов. `guard` создан именно для этого: он формулирует условие, которое должно выполняться, а его блок `else` срабатывает, когда оно не выполняется.
```swift
func priceFor(_ quantity: Int) throws -> Int {
    guard quantity > 0 else {
        throw OrderError.notPositive
    }
    return quantity * 3
}
```
Блок `else` у `guard` обязан покинуть текущую область видимости, и `throw` — один из способов это сделать, наряду с `return`, `break` и `continue`. Несколько `guard` подряд в начале функции читаются как список правил, которым входные данные должны удовлетворять.

---

Иногда неважно *почему* что-то завершилось неудачей, — важно лишь то, что это произошло. `try?` превращает вызов с `throws` в **опциональное значение**: значение при успехе, `nil` при выброшенной ошибке.
```swift
enum ParseError: Error {
    case notANumber
}

func toInt(_ text: String) throws -> Int {
    guard let value = Int(text) else {
        throw ParseError.notANumber
    }
    return value
}

if let number = try? toInt("42") {
    print(number) // 42
}
```
Никакого `do`, никакого `catch`: сбой спрятан в опциональное значение, разворачивать которое вы уже умеете. Плата за это — потерянное значение ошибки, поэтому прибегайте к `try?` только тогда, когда сообщать действительно не о чем.

---

Поскольку `try?` даёт опциональное значение, оператор объединения nil `??` доводит дело до конца, подставляя запасное значение:
```swift
let port = (try? readPort(text)) ?? 8080
```
Круглые скобки важны. Без них `try?` попытался бы покрыть всё выражение целиком, включая `??`, а компилятор требует явно указать, где заканчивается вызов, который может завершиться неудачей.

Прочитайте строку как одно предложение: *взять порт, который удалось прочитать, иначе 8080*. Две строки `do`/`catch` сжимаются в одну, когда восстановление — это действительно просто значение по умолчанию.

---

Есть и третья форма: `try!`. Она говорит компилятору *этот вызов не может завершиться неудачей*, поэтому не нужны ни `do`, ни `catch`, ни опциональное значение. Если вызов всё же не удастся, программа немедленно остановится.
```swift
let pattern = try! Regex("[0-9]+")
```
Именно в такой ситуации `try!` оправдан: аргумент — литерал, написанный вами в вашем собственном коде, и если он неверен, программа сломана и должна остановиться уже при первом же запуске.

Всё, что приходит во время выполнения, — строка, введённая пользователем, файл, ответ сети — может оказаться неверным так, как не заметить при написании кода, и `try!` на таком вызове превращает устранимый сбой в падение на глазах у пользователя. Здесь используйте `do`/`catch` или `try?`.

---

Когда функция выбрасывает ошибку, всё после `throw` пропускается — включая строку, которая должна была закрыть файл или освободить блокировку. `defer` решает эту проблему: он регистрирует блок сразу, а выполняет его, когда заканчивается текущая область видимости, каким бы образом она ни закончилась.
```swift
func load() throws {
    print("open")
    defer { print("close") }
    throw FileError.missing
}
```
Этот вызов печатает `open`, затем `close`, и только потом ошибка уходит вызывающему коду. Вернись функция обычным образом, `close` всё равно напечатался бы — в этом и смысл. Разместите очистку рядом с подготовкой и перестаньте беспокоиться о том, каким выходом завершится код.

---

Одна область видимости может зарегистрировать несколько `defer`. Выполняются они в **обратном** порядке: последний зарегистрированный выполняется первым.

Это не произвольное правило. Очистка обычно отменяет подготовку, шедшую по порядку, — открыть файл, затем заблокировать его, — а отмена должна идти в обратную сторону: разблокировать, затем закрыть. Обратный порядок делает каждый `defer` зеркальным отражением строки над ним.

---

У функции, принимающей замыкание, есть проблема: она не может знать, станет ли переданное ей замыкание выбрасывать ошибку. Пометка функции `throws` заставила бы каждого вызывающего писать `try` — даже тех, кто передаёт безобидное замыкание. `rethrows` говорит *я выбрасываю ошибку, только если её выбрасывает переданное вами замыкание*:
```swift
func applyTwice(_ value: Int, _ transform: (Int) throws -> Int) rethrows -> Int {
    return try transform(transform(value))
}
```
Внутри тела вы по-прежнему пишете `try`, потому что вызов действительно может завершиться неудачей. В месте вызова компилятор смотрит на переданное вами замыкание:
```swift
let doubled = applyTwice(3, { (n: Int) -> Int in n * 2 }) // try не нужен
```
Стандартная библиотека использует это повсюду — `map`, `filter` и `sorted(by:)` все являются `rethrows`, — поэтому перед обычным `map` вы никогда не пишете `try`.

---

Блок `do` не ограничен одним типом ошибки. Каждый шаг может завершиться неудачей по-своему, и каждый сбой получает собственный `catch`:
```swift
do {
    let text = try load(false)
    let value = try parse(text)
    print(value)
} catch NetworkError.offline {
    print("offline")
} catch ParseError.badFormat {
    print("bad format")
} catch {
    print("unknown")
}
```
Первый `try`, выбросивший ошибку, завершает блок, поэтому последующие шаги уже не выполняются — значение просто никогда не существовало. Именно это делает такую форму читаемой: успешный путь остаётся одной прямой строкой сверху, а все способы, которыми всё может пойти не так, перечислены под ним.

---

От того, где стоит блок `do`, зависит, во что обходится один сбой. Поставьте его **внутри** цикла, и тогда каждый элемент получает собственную попытку, поэтому одно плохое значение пропускается, а остальные всё равно выполняются:
```swift
for age in [4, -1, 7] {
    do {
        print(try label(age))
    } catch {
        print("skipped")
    }
}
```
Обернуть же весь цикл в один `do` означало бы остановиться на первой ошибке и никогда не дойти до `7`. Ни один из вариантов не ошибочен — это разница между *одним плохим элементом* и *отказом от попыток*.

---

Всё в этой главе отвечает на один вопрос: кто разбирается со сбоем?

Выбрасывающая ошибку функция отказывается на него отвечать. Она называет, что пошло не так, — вариант перечисления `Error`, несущий всё, что понадобится обработчику, — и передаёт решение выше. Затем вызывающий код выбирает инструмент: `do`/`catch`, чтобы реагировать по каждому варианту отдельно, `try?` и `??`, чтобы вернуться к значению по умолчанию, `defer`, чтобы прибраться на выходе в любом случае.

Именно в этом разделении весь смысл. Функция, обнаружившая проблему, редко знает, что должно произойти дальше, а код, который это знает, редко хочет повторять проверку.

**コメント**は、ソースコードの中に書かれる、コードを読む人のためのメモです。コンパイラはコメントを完全に無視するので、プログラムの動作が変わることはありません。

最もシンプルなコメントは**1行コメント**です。`//`で始まり、行の終わりまで続きます。
```kotlin
// Greets the user
println("Hello")
```
コメントは、コードが何のためのものか、なぜそのように書かれたのかを説明するために使います。

---

コメントは独立した行である必要はなく、同じ行のコードの後ろに置けます。これは**行末コメント**と呼ばれ、その文についての短いメモを書くのに適した場所です:
```kotlin
val retries = 3 // give up after three attempts
```
`//`から行の終わりまではすべて無視され、手前のコードは通常どおり実行されます。

---

コンパイラはコメントを完全に取り除くので、コメントの追加や削除がプログラムの動作を変えることはありません。実行されるのは、コメントされて**いない**コードだけです。

そのため、`//` はコードの行を削除せずに無効にする手軽な方法になります。これは**コメントアウト**と呼ばれます:
```kotlin
var total = 10
// total = total + 5
println(total) // prints 10
```
2行目は今やコメントなので、`total` は `10` のままです。`//` を取り除けば、その行は再び有効になります。

コメントアウトは実験している間は便利ですが、後片付けを忘れないでください。長い間コメントアウトされたままのコードは、次に読む人を混乱させるだけです。

---

コメントが複数行にわたるときは、Kotlinの**複数行コメント**（ブロックコメントとも呼ばれます）が使えます。`/*`で始まり `*/` で終わり、間にあるものは改行も含めてすべて無視されます。
```kotlin
/*
  Prints the welcome banner.
  Called once when the app starts.
*/
println("Welcome!")
```
ブロックコメントは短くして1行に収めることもできます: `/* like this */`

---

`//`は行の終わりで止まりますが、`/*` コメントは `*/` に達するまで止まりません。閉じるのを忘れると、コンパイラはその後のすべてのコードをコメントの一部として扱い、エラーを報告します:
```kotlin
val width = 10 /* in centimetres
println(width) // still inside the comment: error, the comment is never closed
```
`//`と `/* */` はどちらも行末コメントとして使えますが、`/*` の場合は `*/` があることを必ず確認してください。

---

Javaではブロックコメントの中に別のブロックコメントを含められませんが、Kotlinでは**ネストできます**。それぞれの `/*` には対応する独自の `*/` が必要で、コメントは最も外側のものが閉じられたときにだけ終わります。
```kotlin
/* outer /* inner */ still a comment */
println("done")
```
ここで `still a comment */` は外側のコメントの一部なので、出力されるのは `done` だけです。この仕組みのおかげで、すでに `/* */` コメントを含んでいるコードブロック全体でもコメントアウトできます。

---

複数行を一度にコメントアウトするには、各行に `//` を追加する代わりに、それらを1つのブロックコメントで囲みます:
```kotlin
var total = 100
/*
total = total - 30
total = total - 20
*/
println(total) // prints 100
```
ネストのおかげで、その中の行にすでに `/* */` コメントが含まれていても機能します。

---

ブロックコメントの一般的な使い方の1つが**ヘッダーコメント**です。関数の直上に置かれる短いブロックで、その関数が何をするのか、パラメーターが何を意味するのかを説明します。
```kotlin
/*
Returns the number of seconds in the given minutes.
minutes is a whole number, never negative.
*/
fun toSeconds(minutes: Int): Int {
    return minutes * 60
}
```
`toSeconds` を呼び出す人は、本体を読む代わりにヘッダーを読めます。ヘッダーは関数の隣に置き、一緒に更新するようにしてください。

---

Kotlinには3つ目のコメントとして**ドキュメンテーションコメント**があります。**KDoc**と呼ばれる形式で書かれ、`/**`（スラッシュと2つのアスタリスク）で始まり `*/` で終わり、関数、クラス、プロパティの直上に置かれます。
```kotlin
/**
 * Returns the greeting for [name].
 */
fun greet(name: String): String {
    return "Hi, $name!"
}
```
コンパイラにとっては単なるコメントですが、IntelliJ IDEAのようなツールはこれを読み取り、`greet` のヘルプテキストとして表示します。内側の行の先頭にある `*` は、ブロックを揃えておくための単なる慣習です。KDocの中ではMarkdownが使え、`[name]` のような角括弧はそのパラメーターへのリンクになります。

---

ドキュメンテーションコメントの最初の行は**要約**です。関数が何をするのかを述べる短い文です。三人称で、関数を説明するかのように書きます:「Returns...」「Adds...」「Checks...」など。
```kotlin
/**
 * Returns `true` when [n] is divisible by two.
 */
fun isEven(n: Int): Boolean {
    return n % 2 == 0
}
```
コメントは宣言のすぐ上に、間に他の文を挟まずに置く必要があります。そうしないと、ツールはそのコメントを関数に結び付けません。

---

要約の後に、ドキュメンテーションコメントは**KDocタグ**でパラメーターと戻り値を説明できます。KDocタグは常に `@` で始まります:
```kotlin
/**
 * Returns the number of seconds in the given minutes.
 * @param minutes a whole number of minutes, never negative
 * @return [minutes] multiplied by sixty
 */
fun toSeconds(minutes: Int): Int {
    return minutes * 60
}
```
`@param` の後にはパラメーターの名前が続き、その後に説明が来ます。パラメーターごとに `@param` が1つあります。`@return` は関数が返す値を説明します。順序は常に同じです。まず要約、次に `@param` タグ、そして `@return` です。

---

パラメーターが複数ある関数では、パラメーターごとに `@param` タグが1つ付き、パラメーターと同じ順序で書かれます:
```kotlin
/**
 * Returns the area of a rectangle.
 * @param width the horizontal side, in centimetres
 * @param height the vertical side, in centimetres
 * @return the product of [width] and [height]
 */
fun area(width: Int, height: Int): Int {
    return width * height
}
```
タグはあくまでコメントです。パラメーターの名前を変えてタグを更新し忘れても、何も壊れませんが、ドキュメントは嘘をつき始めます。KDocはシグネチャと一緒に更新してください。

---

コンパイラがコメントを探すのはコードの中だけで、**文字列リテラル**の中では決してありません。ダブルクォートの間では、`//` と `/* */` は普通の文字にすぎません:
```kotlin
println("50 // 2") // prints 50 // 2
```
最初の `//` はテキストの一部であり、2つ目が本当のコメントを始めます。これに最も驚かされるのはウェブアドレスです。プロトコルの直後に `//` が含まれています。

---

エディタが理解する慣習に従うコメントもあります。最も一般的な**マーカー**は次のとおりです:
- `// TODO: ...` は、まだ書く必要があるものを示します
- `// FIXME: ...` は、間違っていることが分かっていて修正が必要なコードを示します

```kotlin
val limit = 10
// TODO: read the limit from the settings
```
コンパイラにとってそれらは普通のコメントですが、IntelliJ IDEAは専用のツールウィンドウに集めるので、残っている作業を見つけやすくなります。`TODO` は通常、本物の実装が書かれるまでコードをコンパイル可能に保つプレースホルダーの隣に置かれます。作業を終えたら、同じ変更の中でプレースホルダーを置き換え、マーカーを取り除いてください。そうすれば、コメントがコードの状態について嘘をつくことはありません。

---

`FIXME` は `TODO` とは異なります。コードはすでに存在していて、間違っていることが分かっているのです。良い `FIXME` はバグが何かを述べ、可能であればそれを示す例を添えます。そうすれば、次の人が素早く修正できます。`TODO` と同じように、バグが修正されたらマーカーは削除しますが、まだ正しいドキュメンテーションコメントは残します。

---

良いコメントは、コードが**何を**しているのかではなく、**なぜ**そうしているのかを説明します。コードは何が起きるかをすでに示しています。それを言葉で繰り返すのはノイズを増やすだけで、コードが変わるとすぐに古くなります:
```kotlin
// set timeout to 30
val timeout = 30
```
その数の背後にある理由こそ、読む人には推測できないものです:
```kotlin
// the server drops idle connections after 35 seconds, so stop earlier
val timeout = 30
```
コメントがその下の行を言い換えているだけなら、削除するか理由に置き換えてください。最良のコメントは、コードでは語れないことを語るものです。

**コメント**とは、ソースコードの中に読む人のために書かれる注釈のことです。コンパイラはコメントを完全に無視するため、プログラムの動作が変わることはありません。

最もシンプルなコメントは**1行コメント**です。`//`で始まり、行の終わりまで続きます。
```swift
// Greets the user
print("Hello")
```
コメントは、コードが何のためのものか、なぜそのように書かれたのかを説明するために使います。

---

コメントは専用の行を持つ必要はなく、同じ行でコードの後に続けることができます。これは**行末コメント**と呼ばれ、その特定の文についての短いメモを書くのに適した場所です:
```swift
let retries = 3 // give up after three attempts
```
`//`から行の終わりまではすべて無視され、その前のコードは通常どおり実行されます。

---

コンパイラはコメントを完全に取り除くため、コメントを追加したり削除したりしても、プログラムの動作は決して変わりません。実行されるのは、コメント化**されていない**コードだけです。

このため、`//`はコードの行を削除せずに無効にする手軽な方法になります。これは**コメントアウト**と呼ばれます:
```swift
var total = 10
// total = total + 5
print(total) // prints 10
```
2行目はコメントになったため、`total`は`10`のままです。`//`を取り除くと、その行は再び実行されるようになります。

コメントアウトは実験している間は便利ですが、後片付けを忘れないでください。長い間コメントアウトされたままのコードは、次に読む人を混乱させるだけです。

---

コメントが複数行にわたる場合は、Swiftの**複数行コメント**(ブロックコメントとも呼ばれます)を使えます。`/*`で始まり`*/`で終わり、間にあるものは改行も含めてすべて無視されます。
```swift
/*
  Prints the welcome banner.
  Called once when the app starts.
*/
print("Welcome!")
```
ブロックコメントは短くして1行に収めることもできます: `/* like this */`

---

行の終わりで止まる`//`とは異なり、`/*`コメントは`*/`に達するまで止まりません。閉じるのを忘れると、コンパイラはそれ以降のコードをすべてコメントの一部として扱い、エラーを報告します:
```swift
let width = 10 /* in centimetres
print(width) // still inside the comment: error, the comment is never closed
```
`//`も`/* */`も行末コメントとして使えますが、`/*`を使うときは必ず`*/`があることを確認してください。

---

多くの言語ではブロックコメントの中に別のブロックコメントを含めることはできませんが、Swiftでは**ネストできます**。すべての`/*`には対応する`*/`が必要であり、コメントは最も外側のものが閉じられたときにのみ終わります。
```swift
/* outer /* inner */ still a comment */
print("done")
```
ここで`still a comment */`は外側のコメントの一部なので、出力されるのは`done`だけです。これにより、すでに`/* */`コメントを含むコードのブロック全体でもコメントアウトできます。

---

複数の行を一度にコメントアウトするには、各行に`//`を追加するのではなく、1つのブロックコメントで囲みます:
```swift
var total = 100
/*
total = total - 30
total = total - 20
*/
print(total) // prints 100
```
ネストのおかげで、それらの行の1つにすでに`/* */`コメントが含まれている場合でも機能します。

---

ブロックコメントの一般的な使い方は**ヘッダーコメント**です。関数のすぐ上に置かれる短いブロックで、関数が何をするか、パラメータが何を意味するかを説明します。
```swift
/*
Returns the number of seconds in the given minutes.
minutes is a whole number, never negative.
*/
func toSeconds(_ minutes: Int) -> Int {
    return minutes * 60
}
```
`toSeconds`を呼び出す人は、本体を読む代わりにヘッダーを読むことができます。ヘッダーは関数の隣に置き、一緒に更新されるようにしてください。

---

Swiftには3つ目のコメントである**ドキュメンテーションコメント**があります。`///`(スラッシュ3つ)で始まる1行コメントで、関数、型、プロパティのすぐ上に置かれます。
```swift
/// Returns the greeting for `name`.
func greet(_ name: String) -> String {
    return "Hi, \(name)!"
}
```
コンパイラにとっては単なるコメントですが、Xcodeのようなツールはこれを読み取り、`greet`のヘルプテキストとして表示します。ドキュメンテーションコメントは**Markdown**をサポートしているため、コードにはバッククォート、`**太字**`、リストを使えます。

---

ドキュメンテーションコメントの最初の行は**要約**です。関数が何をするかを述べる短い文です。三人称で、関数を説明するかのように書きます: 「Returns...」「Adds...」「Checks...」。
```swift
/// Returns `true` when `n` is divisible by two.
func isEven(_ n: Int) -> Bool {
    return n % 2 == 0
}
```
コメントは宣言のすぐ上に、間に空行を入れずに置く必要があります。そうしないと、Xcodeはそれを関数に紐付けません。

---

ドキュメンテーションコメントにはブロック形式もあります。`/**`で始まり`*/`で終わります。複数行コメントとまったく同じですが、最初にアスタリスクが1つ余分に付きます。
```swift
/**
 Returns the greeting for `name`.

 The result always ends with an exclamation mark.
 */
func greet(_ name: String) -> String {
    return "Hi, \(name)!"
}
```
`/// text`と`/** text */`はツールにとって同じ意味です。`///`はSwiftコードで最も一般的な選択肢であり、`/** */`は長い説明に便利です。単なる`/* */`や`//`のコメントは、関数の上に置かれていてもドキュメンテーションでは**ありません**。

---

要約の後に、ドキュメンテーションコメントはXcodeが認識する特別なMarkdownのリスト項目で、パラメータと戻り値を説明できます:
```swift
/// Returns the number of seconds in the given minutes.
/// - Parameter minutes: a whole number of minutes, never negative
/// - Returns: `minutes` multiplied by sixty
func toSeconds(_ minutes: Int) -> Int {
    return minutes * 60
}
```
順序は常に同じです。最初に要約、次にパラメータごとに`- Parameter name:`、そして`- Returns:`です。

---

一部のコメントは、エディタが理解できる規約に従っています。Swiftで最も一般的な**マーカー**は次のとおりです:
- `// MARK: - Title`はファイルのセクションにラベルを付け、Xcodeのナビゲーションメニューに表示されます
- `// TODO: ...`は、まだ書く必要があるものを示します
- `// FIXME: ...`は、間違っていることが分かっていて修正が必要なコードを示します

```swift
// MARK: - Setup
let limit = 10
// TODO: read the limit from the settings
// FIXME: crashes when the list is empty
```
コンパイラにとってそれらは普通のコメントですが、Xcodeはそれらを一覧表示するため、残っている作業を見つけやすくなります。作業が終わったらマーカーを削除してください。古くなった`TODO`は誤解を招きます。

---

`TODO`は通常、本物の実装が書かれるまでコードをコンパイル可能な状態に保つプレースホルダーの隣に置かれます。作業を完了したら、同じ変更の中でプレースホルダーを置き換え、マーカーを削除してください。そうすれば、コメントがコードの状態について嘘をつくことはありません。

---

`FIXME`は`TODO`とは異なります。コードはすでに存在しますが、間違っていることが分かっています。良い`FIXME`はバグが何かを述べ、可能であればそれを示す例を挙げるため、次の人が素早く修正できます。`TODO`と同様に、バグが修正されたらマーカーは削除しますが、まだ正しい情報を伝えているドキュメンテーションコメントは残してください。

---

良いコメントは、コードが**何を**しているかではなく、**なぜ**そうしているかを説明します。コードはすでに何が起こるかを示しているため、それを言葉で繰り返すのはノイズを増やすだけで、コードが変わるとすぐに古くなります:
```swift
// set timeout to 30
let timeout = 30
```
その数の背後にある理由こそ、読む人が推測できないものです:
```swift
// the server drops idle connections after 35 seconds, so stop earlier
let timeout = 30
```
コメントがその下の行を言い換えているだけなら、削除するか理由に置き換えてください。

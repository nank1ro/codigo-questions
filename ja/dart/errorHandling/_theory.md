実行できない文というものがあります：数字ではないテキストの読み取り、リストの末尾を越えた要素の取り出し、空のリストの最初の項目を要求すること。そのようなとき、Dart は失敗を記述するオブジェクトを**投げます**。

`throw` キーワードを使えば、自分でも1つ投げられます。`Exception('message')` は短い説明を運んだ、できあいのオブジェクトを作ります：

```dart
throw Exception('no fuel');
```

throw は `return` ではありません。投げられると、その文、その関数、そしてその上にあるすべての呼び出し元を放棄し、それを処理するものを探します。どこにも見つからなければ、プログラムは停止して失敗を出力します：

```
Unhandled exception:
Exception: no fuel
```

throw の後のすべてはスキップされるので、本来なら実行されるはずだった行は決して実行されません。このトピックの要点はまさにそこにあります：プログラムを終わらせてしまう代わりに、失敗をどこで処理するかを決めることです。

---

プログラムを生かしておくには、危険な文を `try` ブロックで囲み、回復の方法を `catch` ブロックに記述します：

```dart
try {
  print(int.parse('twelve'));
} catch (e) {
  print('that is not a number');
}
```

テキストが整数を表していないとき、`int.parse` は投げます。Dart は投げる最初の文で `try` ブロックを抜け、残りをスキップし、`catch` ブロックを実行し、それから後ろに続くコードに進みます。括弧の中の変数、ここでは `e` は、投げられたオブジェクトそのものです。

`try` ブロックの中で起きたことは何も元に戻されないので、ブロックは予期する失敗に見合うだけ短く保ちます。

---

むき出しの `catch` はすべてを受け入れるため、計画していなかった失敗まで隠してしまいます。ちょうど1種類だけを処理するには、`on` 節にその型を名前で指定します：

```dart
try {
  return int.parse(text);
} on FormatException catch (e) {
  return -1;
}
```

テキストが整数でないとき、`int.parse` は **`FormatException`** を投げるので、入力を読むときに指定すべき型はこれです。`on` 節はその型とそのサブタイプにだけ一致し、それ以外には何も一致しません：ほかの失敗はそのまま外へ伝播し、そのためのものではなかった回復に飲み込まれる代わりに、やはり表面に現れます。

---

1つの `try` ブロックの後ろには**複数の**節を続けられ、それぞれが別々の失敗から回復します。Dart は投げられたオブジェクトを上から下へ各節と比較し、一致した**最初の**ものを実行します：

```dart
try {
  return names[int.parse(text)];
} on FormatException {
  return 'not a number';
} on RangeError {
  return 'out of range';
} catch (e) {
  return 'unknown problem';
}
```

存在しないインデックスでリストを読むと **`RangeError`** が投げられるので、その1行のもつ2つの失敗は別々の答えを受け取ります。

最初に一致したものが勝つため、順番が重要です：より具体的な節の上に一般的な型のための節を置くと、それが常に勝ち、具体的な節は決して実行されなくなります。具体的な節を先に書き、安全網がほしければむき出しの `catch` を最後に書きます。

上の `on RangeError` 節は、複数の節をどう並べるかを見せるためだけにあるものです。`RangeError` は、プログラムが制御できない状況ではなく、コードの間違いを知らせるものです。そのような失敗は捕まえる代わりに防ぐべきである理由は、後の練習で説明します。

---

多くの場合、回復に投げられたオブジェクトはまったく必要ありません：型がすでにすべてを語っています。その場合は `catch` の部分を落とし、`on` 節だけを残します：

```dart
try {
  return int.parse(text);
} on FormatException {
  return 0;
}
```

2つの形式の違いは、変数を受け取るかどうかだけです：

- `on FormatException catch (e)` — その型に一致し、オブジェクトを `e` として渡してくれる
- `on FormatException` — その型に一致するが、変数はない
- `catch (e)` — すべてに一致し、オブジェクトを渡してくれる

使わない変数を省くことで、ハンドラーが実際に使うものがはっきりします。

---

ハンドラーの後ろには3つ目のブロックを続けられます。`finally` は**どんな場合でも**実行されます：`try` ブロックが普通に終わった後、ハンドラーが回復した後、そして何も一致せず失敗がまだ外へ伝播しているときにも。

```dart
try {
  return 'parsed ${int.parse(text)}';
} on FormatException {
  return 'failed';
} finally {
  print('done');
}
```

`return` が値を渡し戻す前でさえ実行されるので、上のメッセージは呼び出し元が結果を見る前に出力されます。そのため `finally` は、開いたものを閉じるような、どのみち実行しなければならない仕事の場所になります。

---

あなた自身のコードも、ライブラリと同じやり方で投げます。`Exception('message')` は短い説明を持つ素朴な例外を作り、`throw` がそれを送り出します：

```dart
if (amount > balance) {
  throw Exception('insufficient funds');
}
```

メッセージは失われません：`toString()` は `Exception` という語とコロンとメッセージをつなげます。これはまさに未処理の例外のレポートが出力する内容です。

```dart
print(Exception('insufficient funds')); // Exception: insufficient funds
```

投げることは `-1` のようなでっち上げの値を返すことに勝ります：呼び出し元はそれを見ることを忘れられませんし、理由も一緒に運ばれます。

---

ハンドラーが回復するのにふさわしい場所ではないこともあります：失敗に*気づく*だけにして、実際に対処できる呼び出し元へ伝播させ続けたい場合です。`rethrow` キーワードは `catch` や `on ... catch` ブロックの中でそれを行います：

```dart
try {
  return int.parse(text);
} on FormatException {
  log.add('bad input: $text');
  rethrow;
}
```

`rethrow` は**同じ**オブジェクトを先へ送るので、呼び出し元は元の失敗を見ます。代わりに `throw e` と書いても動きますが、旅をやり直すことになり、失敗が最初に起きた場所が失われます。

同じ文の `finally` ブロックは、外へ出ていく途中でも実行されます。

---

`catch` 節は**2つ目の**引数を受け取れます：

```dart
try {
  return int.parse(text);
} on FormatException catch (e, s) {
  log.add('$e');
  log.add('$s');
  rethrow;
}
```

1つ目は投げられたオブジェクト、2つ目は `StackTrace`：投げられた瞬間に実行されていた呼び出しの連なりです。これは失敗が*どこから*来たのかに答えてくれます。メッセージだけではめったに分からないことです。

スタックトレースはファイル名、行番号、フレームを並べ、ビルドや呼び出し経路によって変わります。出力し、レポートに添え、先へ渡してください — しかし決して固定のテキストと比較してはいけませんし、その中身の上にプログラムの動作を組み立ててもいけません。記録するつもりのあるときだけ求めてください。

---

`Exception` はインターフェースなので、あなた自身のクラスもその一つになれます。独自の例外は、失敗に `on` 節で選べる名前を与え、ハンドラーが読めるフィールドを与えます：

```dart
class EmptyCartException implements Exception {
  final String message;

  EmptyCartException(this.message);

  @override
  String toString() => 'EmptyCartException: $message';
}

throw EmptyCartException('nothing to pay for');
```

押さえておきたい部分は3つです：クラスを他の失敗と同じ仲間にするための `implements Exception`、詳細を運ぶ `final` フィールド、そして未処理の例外のレポートを読みやすくするためにオーバーライドした `toString()` です。このオーバーライドがないと、Dart はむき出しのクラス名を出力し、詳細は失われます。

---

Dart は2つの系統のオブジェクトを投げ、それらは正反対のことを意味します。

**`Exception`** は、プログラムが制御できなかった状況を表します：数値でなかったテキスト、存在しなかったファイル、何も答えなかったネットワークなどです。`FormatException` はその一つです。これらは予期されるもので、捕まえるのが普通の応答です。

**`Error`** は、コード自体の間違いを表します：

- `ArgumentError` — 無効だと文書化されている値で関数が呼ばれた
- `StateError` — 求められたことができない時点でオブジェクトが使われた
- `RangeError` — インデックスや値が許された範囲の外だった

`Error` を捕まえることは、バグを直す代わりに隠すことです。正しい答えは、それが投げられなくなるようにコードを変えることです：呼ぶ前に引数を確認するか、投げない API を使います。`on FormatException` 節が良い習慣である一方、`on ArgumentError` 節がほとんど常にそうでないのは、このためです。

---

ライブラリの中には、まったく投げない版を用意しているものもあります。`int.parse` の隣に、Dart には **`int.tryParse`** があります：変換は同じですが、テキストが数値でないときは投げる代わりに `null` を返します。

```dart
print(int.parse('42'));     // 42
print(int.tryParse('42'));  // 42
print(int.tryParse('42x')); // null
```

結果は `int?` なので、`??` 演算子がそのままデフォルト値に変えてくれます：

```dart
final port = int.tryParse(text) ?? 8080;
```

失敗がありふれたもので、代わりの値がほしいだけなら、これは `try` ブロックより短くて分かりやすいです。不正なテキストが本当に、上の誰かが知らなければならない失敗であるときのために `int.parse` を取っておきましょう。

---

`firstWhere` は、テストに一致する最初の要素を返します。何も一致しないときは返す要素がないので、`StateError` を投げます：

```dart
final words = ['a', 'fg'];
print(words.firstWhere((w) => w.length > 3)); // Bad state: No element
```

`int.tryParse` と同じく、ライブラリは逃げ道も用意しています。名前付き引数 `orElse` は、何も一致しなかったときに使う値を作る関数を受け取ります：

```dart
print(words.firstWhere((w) => w.length > 3, orElse: () => 'none')); // none
```

選び方は前と同じです：「何も一致しない」がありふれた結果なら `orElse` を、データが壊れていて誰かが知らなければならないことを意味するなら引数なしの呼び出しを使います。

---

`throw` と `try` は同じ関数の中にある必要はありません。仕事ができない関数が投げ、それについてどうすべきか知っている呼び出し元が捕まえます：

```dart
int ageFromText(String text) {
  final age = int.tryParse(text);
  if (age == null) throw FormatException('not a number');
  return age;
}
```

`ageFromText` は、不正な年齢がプログラムを終わらせるべきか、メッセージを表示すべきか、読み飛ばすべきかについて意見を持ちません — それは呼び出し元の決定であり、呼び出し元こそ `try` ブロックのあるべき場所です。この分担こそ、`-1` を返すより投げることに価値がある理由です：失敗は、それに答えられる唯一の場所に届きます。

`try` ブロックは最初の失敗で止まるので、失敗した呼び出しの後ろの文も飛ばされることを覚えておいてください。

---

`try` ブロックをどこに置くかが、1つの失敗がどれだけの仕事を壊すかを決めます。ループの周りに置くと、最初の不正な要素がバッチ全体を終わらせます。ループの**中**に置くと、失われるのはその要素だけで、残りは処理され続けます：

```dart
for (final text in texts) {
  try {
    total += int.parse(text);
  } on FormatException {
    continue;
  }
}
```

これはファイルの取り込み、設定の一覧の読み取り、メッセージの待ち行列の処理といった日常的な形です：壊れた行が1つあっても、正しい行まで捨てるべきではありません。規則は前と同じです — `try` ブロックは失敗しうる文の周りに置き、それより大きくしないことです。

---

最後の要素は、わざと `Error` を投げることです。何を受け付けるかを文書化している関数は、それ以外を大きな声で拒むべきで、`ArgumentError` がそのためのオブジェクトです：

```dart
int setVolume(int level) {
  if (level < 0 || level > 100) {
    throw ArgumentError('level must be between 0 and 100');
  }
  return level;
}
```

メッセージは `e.message` で取り出せ、`toString()` は `Invalid argument(s): ` に続けてそれを出力します。

これは前の規則と矛盾しません。`ArgumentError` を投げるのは正しく、捕まえるのは正しくありません：それは*呼び出し元*の書き手に、その呼び出し自体が間違っていると伝えるものであり、直し方は呼び出しの周りのハンドラーではなく、呼び出す前の確認だからです。
